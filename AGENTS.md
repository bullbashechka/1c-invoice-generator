# Правила работы с проектом

## Общение

- Писать кратко и прямо, без эмодзи, вводных фраз, похвалы, эмоционального смягчения и предложений продолжить работу. Не задавать вопросы. Завершать ответ после передачи результата.
- Различать требования, фактическую реализацию, результаты проверок и неподтверждённые предположения. В отчёте указывать изменённые файлы, выполненные проверки и оставшиеся ограничения.

## Назначение и состояние

Проект связывает документ «Заказ клиента» в 1С:КА для Казахстана с задачей Битрикс24. Название репозитория не определяет объём продукта: формирование Word-документов и счета внутри Б24 отложены; выставление счетов остаётся в КА. Источник согласованных требований — `PRD.md`; начинать работу с его актуального содержимого, особенно разделов 9–12.

В репозитории пока находится исторический браузерный прототип внешней обработки, а не целевая встроенная интеграция. Он обрабатывает клиентское оповещение `Запись_ЗаказКлиента`, проверяет режим проведения и `ПринудительноЗакрытьФорму`, затем открывает фиксированный HTTPS-адрес новой задачи. Обработка должна оставаться открытой в том же сеансе. Возврат связи и обратное создание заказа этим кодом не реализованы.

`src/stage-1-prototype/` — отдельный незавершённый прототип расширения T05: группа формы заказа и собственный регистр связи. Блок подтверждён в существующем и новом незаписанном заказе. Дефект повторного идентификатора операции воспроизведён в 1С, исправлен и проверен повторным прогоном: точный повтор, оба конфликта и сохранность первой связи прошли. Конкурирующие сеансы не проверены. Синтаксис и применимость пройдены; полная проверка обработчиков заимствованных форм остаётся открытой. Колонка после «Клиент», заполнение из собственного регистра и очистка после обновления подтверждены в живом списке синтетической связью; переход в Б24 ещё отсутствует. Подключение к успешному «Провести и закрыть» подтверждено диагностическим событием; обычная запись, проведение без закрытия, штатный отказ и существующая синтетическая связь его не вызывают. Б24 и сервис этим обработчиком не вызываются. Не считать прототип рабочей интеграцией или готовой поставкой; актуальные результаты — `docs/stage-1-prototypes.md`.

Тестовая среда по PRD: 1С:Предприятие 8.3.23.2040, «Комплексная автоматизация для Казахстана», редакция 2, версия 2.4.5.18. Рабочая база описана как файловая в сетевой папке; её актуальную конфигурацию и клиентские ОС нельзя выводить из версии тестовой среды.

## Карта файлов

- `PRD.md` — согласованное поведение, приёмка и открытые технические вопросы.
- `TASKS.md` — план с сохранённой историей этапа 0; `docs/stage-1-prototypes.md` — фактические проверки и препятствия этапа 1.
- `src/stage-1-prototype/` — штатная XML/BSL-выгрузка прототипа расширения из демобазы; границы и воспроизведение описаны в его `README.md`.
- `README.md` — краткое описание и ссылка на настройку MCP.
- `src/Открытие_b24/` — выгрузка внешней обработки в BSL/XML; основной модуль: `src/Открытие_b24/Открытие_b24/Forms/Форма/Ext/Form/Module.bsl`.
- `src/Открытие_b24/Открытие_b24/Forms/Форма/Ext/Form.xml` — элементы, реквизиты и привязки обработчиков управляемой формы.
- `Открытие_b24_модуль_формы.bsl` — отдельная копия основного модуля. При изменении прототипа сохранять обе копии одинаковыми.
- `Открытие_b24.epf` — бинарная обработка. Правка BSL/XML сама по себе не обновляет этот файл.
- `mcp/README.md` — инструкция переносимого комплекта MCP; `mcp/toolkit/` — сторонний Toolkit, его лицензия, BSL, Python-прокси и нативные компоненты.
- `mcp/MCP_Toolkit_macos.epf`, `mcp/toolkit/build/MCP_Toolkit.epf`, `mcp/toolkit/build/MCP_Toolkit_x86.epf` — готовые обработки для соответствующих ОС и разрядности клиента.

## Ограничения реализации

- Пользовательские сценарии интеграции работают только через десктопное приложение Б24. Браузер нельзя открывать из сценария 1С или использовать как запасной пользовательский путь; исторический HTTPS-переход не переносить в целевую реализацию. Браузер разрешено использовать для диагностики и проверки портала, если пользователь это разрешил. Результаты браузерной проверки не засчитывать как подтверждение поведения десктопного клиента.
- По уточнению пользователя 1 октября 2026 года создание по шаблонам задач не использовать. После временной остановки пользователь возобновил работу; управление ПК разрешено в согласованном объёме проверок.
- Автоматическое открытие формы происходит только после успешного «Провести и закрыть» при отсутствии связи. Обычные запись и проведение его не запускают. Задачу сохраняет сам сотрудник; закрытие формы без сохранения не создаёт задачу.
- Связь строго один к одному. Проверка уникальности и запись должны исключать гонки; повторная доставка восстанавливает связь без дублей и молчаливой замены. Недоступность задачи не означает её удаления.
- Новая задача: название `{Контрагент}.`; постановщик Оксана, исполнитель Люда, проект «Гем платежи», наблюдатель Инга, соисполнитель Женя. Сохранять проверенные ID настроек, не выбирать людей только по именам и не считать `user/30` из прототипа согласованным ID.
- Участники и проект — значения предзаполнения; все поля доступны для ручного изменения в пределах прав Б24, интеграция изменения не отменяет. Постановщик по умолчанию Оксана независимо от инициатора; технически подменять её текущим сотрудником нельзя. Крайний срок подставляется при открытии формы: текущий день, 23:59 UTC+5; пересчёт после полуночи исключён. Описание — данные сохранённого заказа на момент открытия, без дальнейшей синхронизации. Остальные правила заполнения и отображения связи брать из разделов 4–5 PRD.
- Создание заказов из Б24 и действие «Создать в КА» исключены решением пользователя 1 октября 2026 года. T08 и этап 6 исключены, не выполнены. Автоматический возврат ссылки задачи в существующий заказ остаётся обязательным.
- При неизвестном результате проверять прежнюю операцию и временно блокировать повторное создание; потеря ответа не означает отсутствия задачи. Постоянно доступный сервис — кандидат прототипа, не выбранная архитектура; файловая база в сетевой папке сама по себе обработчиком не является. Минимальный контракт: база, заказ, операция, состояние, ID задачи, подтверждение записи.
- Закрытие крестиком не создаёт задачу и не отменяет проведение; повторное «Провести и закрыть» без связи снова открывает форму. Ручная кнопка в несохранённом заказе сначала записывает его без проведения. Сложный интерфейс одновременного создания исключён, атомарная защита связи обязательна.
- Использовать существующий «Гем платежи демо», не добавлять участников и не менять рабочие объекты. Результаты вести в `docs/stage-1-prototypes.md`; права реальных участников и другого сотрудника остаются условием завершения. Историю этапа 0 сохранять.
- Ошибка интеграции не отменяет успешное проведение. Запись связи не должна повторно проводить заказ или запускать создание задачи. Соблюдать восстановление и сроки из раздела 7 PRD.
- Проверять T06/T09, затем T05/T07 и T10 доступными средствами, включая браузерную диагностику по разрешению пользователя. Непроверенные механизмы фиксировать как открытые приёмочные пункты; это не останавливает независимую разработку и подготовку прототипов. Не включать в пользовательский поток неподтверждённое поведение. Браузерный тест не подтверждает поведение десктопного клиента; собственная форма Б24 и автоматическое создание задачи требуют отдельного согласования.
- Целевая функция реализуется расширением конфигурации без изменения основной конфигурации и работает без внешней обработки и MCP. Текущую разработку и проверку выполнять в существующей «КА Демо» по решению пользователя; совместимость с рабочей базой проверить перед внедрением. Поставка — файл расширения `.cfe` с исходниками, инструкциями и указанием проверенных версий платформы, конфигурации и режимов совместимости. После успешной проверки программист устанавливает расширение в рабочую базу с учётом существующих доработок и расширений. Поставка `.cf`, замена основной конфигурации и перенос через сравнение и объединение не входят в выбранный способ внедрения. Если возможностей расширения недостаточно, отдельно согласовать другой способ до его внедрения. Состав интеграционных компонентов согласуется до включения пользовательского потока и внедрения; независимую разработку продолжать.

## Правки и данные

- Перед изменениями выполнить `git status --short`, прочитать затрагиваемые файлы полностью и сохранить чужие незакоммиченные изменения. Не исправлять PRD, Toolkit или бинарники заодно с узкой задачей.
- Сохранять кириллицу и кодировку UTF-8 в текстовых исходниках. Не менять UUID, имена объектов, XML-пространства имён и привязки событий без необходимости; проверять соответствие обработчиков BSL описанию формы.
- При необходимости пересобрать EPF использовать доступный Конфигуратор и зафиксировать способ и версию платформы. Готовой команды сборки основной обработки в репозитории нет; не придумывать её и не объявлять старый бинарник обновлённым.
- `mcp/toolkit/` считать сторонним переносимым комплектом. Менять его только в рамках задачи по Toolkit, сохраняя лицензию. Вложенный workflow сборки macOS-компонентов не является CI основного проекта.
- Секреты, токены, содержимое рабочих баз и персональные пути подключения не включать в исходники, логи и передаваемый `.cfe`. Адреса и доступы задавать настройками.
- `.local/`, `artifacts/`, исходный отдельный клон `mcp/1c-mcp-toolkit/`, базы `*.1CD`, выгрузки `*.dt`, логи и `.env*` исключены корневым `.gitignore`; для `.env.example` предусмотрено исключение. Не обходить исключения принудительным добавлением. UTF-8-исходники и поставляемые EPF отслеживаются Git.

## Исследование репозитория

Use `$code-scout` for non-trivial repository discovery to delegate broad code reading to a lower-cost subagent scout and keep irrelevant file contents out of the primary agent's context.

- Перед использованием прочитать `SKILL.md` навыка `code-scout` и соблюдать его правила назначения задачи и отчёта. Для точечной правки с известными файлами достаточно локального чтения; актуальные отчёты использовать повторно.
- Разведчик исследует код без изменений, сборок и тестов. Основной агент принимает решения, вносит изменения и проверяет результат. Если делегирование недоступно, указать ограничение и провести исследование локально.

## TDD: Red → Green → Refactor

- Для нового поведения и исправления дефектов применять TDD небольшими шагами. Сначала определить наблюдаемый результат по PRD; при исправлении дефекта воспроизвести его и добавить регрессионный тест.
- **Red:** до изменения реализации написать минимальный тест ожидаемого поведения и запустить его. Убедиться, что он падает по нужной причине, а не из-за ошибки теста, окружения или отсутствующих зависимостей. Зафиксировать команду и результат.
- **Green:** внести минимальное изменение, достаточное для прохождения теста. Запустить новый тест и затронутые существующие тесты; не расширять объём правки ради прохождения проверки.
- **Refactor:** после успешных проверок улучшать структуру без изменения поведения. Повторно запускать затронутые тесты после рефакторинга. Следующее требование начинать с нового цикла Red → Green → Refactor.
- Проверять внешний контракт и значимые ошибки, повторные действия и конфликты из PRD. Не писать тесты, которые копируют реализацию или проверяют только заранее заданные ответы заглушек. Моки внешних систем не подтверждают работу в реальной 1С и десктопном Б24.
- Если для изменяемой логики нет тестовой инфраструктуры, добавить минимальный подходящий способ автоматизированной проверки в рамках задачи. Для поведения, доступного только в 1С или десктопном Б24, зафиксировать воспроизводимый сценарий, исходный сбой и результат после исправления в тестовой среде; отдельно указать отсутствие автоматизации.
- Если нужная среда недоступна, явно сообщить, какие проверки не выполнены. Не объявлять цикл TDD завершённым без наблюдаемого исходного сбоя и успешной повторной проверки.
- Для правок только документации, форматирования и других обратимых изменений без изменения поведения не создавать искусственные тесты; проверять сам изменённый артефакт.

## Команды и проверка

Команды ниже выполнять из корня проекта в PowerShell. Основной проект не содержит автоматизированных тестов, настроенного BSL-линтера или скрипта сборки; проверка текста и XML не заменяет запуск в 1С.

```powershell
git status --short
git diff --check
Get-FileHash -LiteralPath 'Открытие_b24_модуль_формы.bsl', 'src/Открытие_b24/Открытие_b24/Forms/Форма/Ext/Form/Module.bsl' -Algorithm SHA256
Get-ChildItem -LiteralPath src -Recurse -Filter '*.xml' | ForEach-Object {
    $null = [xml](Get-Content -LiteralPath $_.FullName -Raw -Encoding UTF8)
}
```

Хеши двух модулей должны совпадать. XML-проверка подтверждает только корректность XML, без проверки схемы метаданных и компиляции BSL. `git diff --check` не проверяет новые неотслеживаемые файлы; их также читать после записи.

Для проверки поведения использовать тестовую базу и тестовые задачи. Прогонять применимые сценарии раздела 9 PRD; отдельно фиксировать версию платформы, конфигурации, десктопного Б24 и ОС. Не представлять статические проверки, макеты или наличие EPF как доказательство работающей интеграции.

MCP — инструмент разработки. По `mcp/README.md` встроенный сервер запускается из соответствующей EPF и подключается по `http://127.0.0.1:6003/mcp`; Python для этого режима не требуется. Обработка и сеанс 1С должны оставаться открытыми. Переносимость готовых сборок на другие компьютеры пока не подтверждена.

Для отдельной задачи по Python-прокси документированы команды ниже; зависимости устанавливаются только при необходимости. Этот запуск не доказывает подключение к базе и работоспособность целевой интеграции.

```powershell
Set-Location mcp/toolkit
python -m venv .venv
& ./.venv/Scripts/python.exe -m pip install -r requirements.txt
& ./.venv/Scripts/python.exe -m onec_mcp_toolkit_proxy
```

Прокси по текущему `__main__.py` слушает `0.0.0.0`, порт по умолчанию 6003. Не считать его доступным только через loopback. Настройки и ограничения описаны в `mcp/toolkit/README.md` и `mcp/toolkit/onec_mcp_toolkit_proxy/config.py`; запуск и подключение выполнять в рамках соответствующей задачи.
