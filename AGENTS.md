# Правила работы с репозиторием

## Назначение и источники требований

Проект связывает «Заказ клиента» в 1С:КА для Казахстана с задачей Битрикс24. Итоговый продукт — расширение `.cfe` без изменения основной конфигурации. Название репозитория не определяет объём продукта.

- `PRD.md` — источник актуальных требований, сценариев и приёмки; перед изменением поведения читать соответствующие разделы, особенно §§3–5 и 7–12.
- `TASKS.md` — актуальный план T46–T67, зависимости и критерии выполнения. Отмечать задачу выполненной только после проверки её критерия.
- `docs/stage-1-prototypes.md` — датированные результаты проверок и ограничения; исторические результаты не подтверждают новый сценарий.
- `docs/stage-1-cleanup.md` — аудит удаления Python-службы и зависимых компонентов.

Согласованный REST-сценарий ещё не реализован и не принят. Сохранённое расширение — незавершённый прототип со старым сервисным адаптером. Python-служба исключена и удалена; не восстанавливать прежние service/SQLite/entity/worker. Прямой HTTPS из расширения — кандидат проверки, а не подтверждённая архитектура.

## Карта репозитория

- `src/stage-1-prototype/` — XML/BSL-исходники прототипа расширения: формы заказа и списка, регистры и обмен. Состояние и способы воспроизведения описаны в его `README.md`.
- `src/Открытие_b24/` — исходники исторической внешней обработки. Модуль формы: `src/Открытие_b24/Открытие_b24/Forms/Форма/Ext/Form/Module.bsl`.
- `Открытие_b24_модуль_формы.bsl` — отдельная копия модуля исторической обработки; при его правке проверять согласованность обеих копий.
- `Открытие_b24.epf` — исходный бинарный прототип для переработки, не итоговое расширение. Правка текстовых исходников сама по себе не обновляет EPF/CFE.
- `tests/stage1/` — сохранённые автоматизированные проверки, диагностика Б24 и BSL-сценарии для демобазы; назначение и ограничения — в `tests/stage1/README.md`.
- `mcp/` — переносимый инструментарий разработки для 1С; настройка — в `mcp/README.md`. `mcp/toolkit/` — сторонний Toolkit, менять только в рамках задачи по нему, сохраняя лицензию.

## Контракт реализации

- Задачу создавать через REST и входящий вебхук только по явной кнопке «Создать задачу в Битрикс24», после успешного штатного проведения заказа. Отказ, ошибка или отмена проведения исключают REST-вызов.
- «Провести и закрыть» только напоминает; обычные запись и проведение не создают задачу. Предварительная форма задачи и автоматическое создание исключены.
- После фиксации устойчивой операции создание выполняется в фоне. Закрытие формы не отменяет попытку. Результат относится к исходному заказу и сообщается инициатору неблокирующим уведомлением без открытия окон и переключения фокуса.
- Связь строго один к одному. Обеспечивать атомарную защиту повторов и конкуренции, сохранность первой связи и восстановление неизвестного результата без повторного создания. Истечение времени не разрешает новую отправку. Подтверждённую неотправку не превращать в автоматическую очередь.
- Ошибка интеграции не отменяет успешное проведение; запись связи не проводит заказ повторно. Ручная привязка, удаление связи, аудит и подтверждение повторного создания определены в PRD.
- Открытие существующей задачи — отдельное действие в десктопном Б24. Браузер исключён из пользовательских переходов; браузерная диагностика не подтверждает работу десктопного клиента.
- Название, описание, роли, точные ID и правило срока брать из актуального PRD §5. Проверять фактические права; не выбирать участников только по именам и не подменять постановщика владельцем вебхука.
- Не добавлять обратное создание заказа, шаблоны задач, вложения, Word, счета внутри Б24 или постоянную синхронизацию: границы — PRD §11.
- Разработку и живые проверки выполнять в существующей «КА Демо» и проекте «Гем платежи демо». Не добавлять участников и не менять рабочие объекты. Дополнительные интеграционные компоненты согласовывать до включения в пользовательский поток.

## Правки и данные

- Перед правками выполнить `git status --short`, прочитать затрагиваемые файлы и сохранить чужие незакоммиченные изменения. Не менять PRD, Toolkit или бинарники заодно с узкой задачей.
- Сохранять UTF-8 и кириллицу. Без необходимости не менять UUID, имена объектов, XML-пространства имён и привязки событий; проверять соответствие обработчиков BSL описанию формы.
- Секрет вебхука, токены и содержимое рабочих баз не включать в исходники, логи, документы и `.cfe`. Настройки и доступы хранить вне поставляемых исходников согласно выбранной и проверенной схеме.
- Соблюдать `.gitignore`; не добавлять принудительно локальные базы, выгрузки, секреты и диагностические артефакты.
- Для сборки и применения расширения использовать штатные средства 1С и фиксировать способ, версии и результат. Не объявлять бинарник обновлённым или поставку готовой только по изменению BSL/XML.

## Исследование репозитория

Use `$code-scout` for non-trivial repository discovery to delegate broad code reading to a lower-cost subagent scout and keep irrelevant file contents out of the primary agent's context.

- Перед использованием прочитать `SKILL.md` навыка `code-scout` и соблюдать его правила назначения задачи и отчёта. Для точечной правки с известными файлами достаточно локального чтения; актуальные отчёты использовать повторно.
- Разведчик исследует код без изменений, сборок и тестов. Основной агент принимает решения, вносит изменения и проверяет результат. Если делегирование недоступно, указать ограничение и провести исследование локально.

## TDD: Red → Green → Refactor

- Для нового поведения и исправления дефектов применять TDD небольшими шагами. Сначала определить наблюдаемый результат по PRD; при исправлении дефекта воспроизвести его и добавить регрессионный тест.
- **Red:** до изменения реализации написать минимальный тест ожидаемого поведения и запустить его. Убедиться, что он падает по нужной причине, а не из-за ошибки теста, окружения или отсутствующих зависимостей. Зафиксировать команду и результат.
- **Green:** внести минимальное изменение, достаточное для прохождения теста. Запустить новый тест и затронутые существующие тесты; не расширять объём правки ради прохождения проверки.
- **Refactor:** после успешных проверок улучшать структуру без изменения поведения. Повторно запускать затронутые тесты после рефакторинга. Следующее требование начинать с нового цикла Red → Green → Refactor.
- Проверять внешний контракт и значимые ошибки, повторные действия и конфликты из PRD. Не писать тесты, которые копируют реализацию или проверяют только заранее заданные ответы заглушек. Моки внешних систем не подтверждают работу в реальной 1С и десктопном Б24.
- Если для изменяемой логики нет тестовой инфраструктуры, добавить минимальный подходящий способ автоматизированной проверки в рамках задачи. Для поведения, доступного только в 1С или десктопном Б24, зафиксировать воспроизводимый сценарий, исходный сбой и результат после исправления в тестовой среде; отдельно указать отсутствие автоматизации.
- Если нужная среда недоступна, явно сообщить, какие проверки не выполнены. Не объявлять цикл TDD завершённым без наблюдаемого исходного сбоя и успешной повторной проверки.
- Для правок только документации, форматирования и других обратимых изменений без изменения поведения не создавать искусственные тесты; проверять сам изменённый артефакт.

## Проверки и фиксация результата

Из корня репозитория:

```sh
git status --short
git diff --check
node --test tests/stage1/*.cjs
python -X utf8 -m unittest discover -s tests/stage1 -p 'test_*.py'
```

Тестовые команды документированы в `tests/stage1/README.md`; запускать проверки, относящиеся к изменению. Сохранённые тесты не подтверждают новую REST-интеграцию. Общая команда сборки или линтинга основного проекта не настроена.

BSL-сценарии выполнять по инструкции `tests/stage1/README.md` только в подходящей демобазе с загруженной версией расширения. Статическая проверка XML, моки и наличие EPF/CFE не заменяют проверки модулей, применимости и поведения в 1С и десктопном Б24.

Документированная демосреда: 1С 8.3.23.2040, КА для Казахстана 2.4.5.18, совместимость прототипа 8.3.21. Перед живым прогоном проверить фактическую среду; не переносить выводы автоматически на рабочую базу.

Результаты живых проверок записывать в `docs/stage-1-prototypes.md`: дата, среда, шаги, ожидаемый и фактический результат, подтверждение и ограничения. В отчёте пользователю различать требования, реализацию и проверенные факты; указывать изменённые файлы, выполненные проверки и непроверенные пункты.
