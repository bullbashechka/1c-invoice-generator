## 2. Среда и установка

Проверенная демосреда: macOS, платформа 1С **8.3.23.2040**, **КА для Казахстана 2.4.5.18**. Внутреннее имя расширения — `Б24ПрототипЭтап1`, назначение — `Customization`, совместимость — **8.3.21**. Поле версии в метаданных не заполнено; версию поставки определяют manifest и контрольная сумма CFE.

1. Сверить фактические версии рабочей платформы и КА, режим совместимости, ОС, доработки заимствованных объектов, другие расширения и права сотрудников. Использовать [перечень объектов](stage-5/object-inventory.md). Результат записать в [бланк внедрения](stage-5/deployment-record.md).
2. Если выявлено существенное отличие или ошибка применимости, остановить установку этой сборки. Заказчик запрашивает архив соответствующей среды; адаптацию выполняем отдельно вместе с ним по данным архива. Основную конфигурацию не заменять и не изменять ради обхода ошибки.
3. Согласовать установку в обед или после работы. Сотрудники сохраняют документы и завершают сеансы. Пока интеграция отключена, создание задач откладывается до её включения.
4. Через штатное управление расширениями загрузить **именно переданный CFE**. Проверить применимость к рабочей конфигурации до подключения. Не использовать `.cf` и сравнение/объединение основной конфигурации.
5. Для этой сборки в демосреде потребовалось снять **безопасный режим только у данного расширения**; защита от опасных действий оставалась включённой. Это известное условие подключения модулей форм, а не проверка рабочей совместимости. Другие настройки защиты не менять заодно.
6. Открыть новый административный сеанс и выполнить первоначальную настройку ниже; сотрудники входят после её завершения в новые сеансы.

Штатные возможности установки, проверки применимости и деактивации описаны в [документации 1С по расширениям](https://1c-dn.com/1c_enterprise/extensions/). Новую установку комплекта в копию базы при его подготовке не выполняли по решению заказчика.

## 3. Первоначальная настройка

Используется входящий вебхук того же портала, что указан в JSON. Полный URL имеет вид `https://<портал>/rest/<ID владельца>/<секрет>/`, обязательно с завершающим `/`. Эта сборка использует классический REST-маршрут; менять его на `/rest/api/` не нужно.

Предоставить вебхуку scopes `task`, `user_basic`, `sonet_group`. Помимо scopes нужны фактические права владельца вебхука на целевой проект, создание и чтение задач с указанными участниками. Владелец вебхука не подменяет постановщика: постановщик задаётся ID 26. Условия scopes и прав описаны в [документации вебхуков Б24](https://github.com/bitrix24/b24restdocs/blob/main/first-steps/first-rest-api-call.md) и [перечне scopes](https://github.com/bitrix24/b24restdocs/blob/main/api-reference/scopes/permissions.md).

| --- | --- | --- |
| `portal` | `https://toofirmagem.bitrix24.kz` | Портал без завершающего `/` |
| `groupId` | 6 | «ГЕМ Общие вопросы» |
| `creatorId` | 26 | Оксана, постановщик |

### Записи регистра

Под административной учётной записью с полными правами открыть **«Функции для технического специалиста» / «Все функции» → «Регистры сведений» → `Расш1_НастройкиОбменаБ24`**. У объекта ошибочный исторический синоним «Расш1 связи заказов б24»; ориентироваться на техническое имя и поля `Ключ`, `Значение`, `Секрет`.

Метаданные разрешают стандартные команды и автоматически создаваемые формы. Такой путь соответствует [стандартному механизму 1С](https://1c-dn.com/download-trial/files/guides/developer_guide.pdf), но заполнение через эту форму при новой установке **не проверено живым прогоном**. Если регистр не открывается или не позволяет запись администратору, настройку не считать выполненной; зафиксировать ограничение и передать заказчику для адаптации по архиву. Не открывать доступ к настройкам всем сотрудникам и не добавлять другой компонент обхода.

1. Создать запись с ключом `stage2Enabled`, значением `false`, пустым полем `Секрет` на время настройки.
2. Создать запись с ключом `rest`. В поле `Значение` вставить содержимое приложенного JSON, в поле `Секрет` отдельно ввести действующий полный URL вебхука. Сохранить запись. Не помещать URL в JSON, исходники, снимки экрана, журналы или этот комплект.
3. Проверить сохранённые несекретные значения и административное ограничение доступа к регистру. `PasswordMode` маскирует поле в форме, но не является шифрованием данных базы; доступ к базе и её копиям должен оставаться административным. По протоколу прямое чтение секрета и запись настроек обычным сотрудником запрещены.
4. В записи `stage2Enabled` установить значение **`true`** — точный текст маленькими буквами без кавычек. Это одноразовый служебный допуск первоначального запуска. Затем оставить эту запись без изменений и управлять паузой через активность расширения.
5. Запись `baseId` вручную не создавать и из демобазы не переносить: расширение создаёт уникальное значение при первой новой операции. Демонстрационные связи, операции и уведомления также не переносить.

Ключ `enabled` относится к старому адаптеру и не включает текущий REST-сценарий. Демонстрационный `rest_settings_setup.bsl` не является инструкцией настройки рабочей базы: в нём ограничения демосреды и проект 36; он не включён в поставку.

## 4. Работа и отключение

Интеграция предназначена для всех сотрудников, работающих в **«Продажи → Заказы клиентов»**, с учётом фактических прав чтения, изменения и проведения заказа. Отдельного списка пилотных пользователей нет.

Задача создаётся только по явной кнопке «Создать задачу в Битрикс24» после успешного штатного проведения заказа. «Провести и закрыть» только напоминает. Дальнейшее создание идёт в фоне; ошибка интеграции не отменяет успешное проведение. ID связи показывается обычным текстом в заказе и списке; переходов и гиперссылок нет.

Для временной паузы администратор **деактивирует всё расширение** штатно в КА и организует завершение прежних сеансов. Новые сеансы работают без кнопок, отображения ID и напоминаний расширения. Для возврата — активировать то же расширение и войти заново. Не удалять расширение: отключение сохраняет его данные. Во время паузы сотрудники ждут включения; ручной обход и автоматическую очередь не вводим.

Отключение расширения не отменяет уже отправленный запрос и не удаляет созданную задачу. Перед паузой дать текущим попыткам завершиться. При неизвестном результате после включения использовать сохранённую операцию: работающий клиент опрашивает состояние примерно раз в 5 секунд. Истечение времени не разрешает повторное создание; известный ID при несохранённой связи восстанавливается штатным механизмом. Это обычное восстановление результата интеграции; восстановление базы из старой копии здесь не рассматривается.

Связи начинаются после рабочего внедрения; предварительной миграции нет. Ранее созданные рабочие и тестовые задачи Б24 оставляются как есть. Новых тестовых задач подготовка комплекта не требует.

## 5. Штатная сборка из исходников

Переданный CFE уже собран, поэтому для установки его пересобирать не нужно. Ниже — воспроизводимая последовательность **для отдельной среды сборки**, по сохранённому протоколу Конфигуратора. Не выполнять её в рабочей базе как часть установки готового CFE.

В среде сборки должна быть КА соответствующей версии. Если расширения ещё нет, создать пустое расширение с внутренним именем `Б24ПрототипЭтап1`. Указать фактический путь к установленной платформе 1С и открыть Конфигуратор с административными правами. Общий префикс пакетного запуска: `1cv8 DESIGNER /F "<база сборки>" /N "<администратор>"`; для серверной базы использовать её штатные параметры подключения вместо `/F`. Путь к программе и подключение зависят от ОС/среды. Пароли в публикуемые команды и отчёт не записывать.

Операции выполняются последовательно; при ошибке следующий шаг не запускать. Для каждой операции сохранять локальный результат Конфигуратора (`/Out "<локальный журнал>"`) и проверять не только код завершения, но и сообщения проверки.

| Шаг | Аргументы после общего префикса |
| --- | --- |
| Загрузить XML/BSL | `/LoadConfigFromFiles "<комплект>/src/stage-1-prototype" -Extension Б24ПрототипЭтап1` |
| Проверить модули | `/CheckConfig -ThinClient -Server -ExternalConnection -ExtendedModulesCheck -Extension Б24ПрототипЭтап1` |
| Проверить применимость | `/CheckCanApplyConfigurationExtensions -Extension Б24ПрототипЭтап1` |
| Применить в базе сборки | `/UpdateDBCfg -Extension Б24ПрототипЭтап1` |
| Выгрузить новую сборку | `/DumpCfg "<новый CFE>" -Extension Б24ПрототипЭтап1` |
| Загрузить её обратно | `/LoadCfg "<новый CFE>" -Extension Б24ПрототипЭтап1` |
| Применить загруженный CFE | `/UpdateDBCfg -Extension Б24ПрототипЭтап1` |

Эти семь операций прошли в существующей КА Демо с кодами 0 при последней сборке. Новая чистая среда по этой инструкции не проверялась. Повторная сборка не обещает тот же бинарный SHA-256; новая версия требует отдельной фиксации и проверки. Переданный CFE не перезаписывать. После применения нужен новый пользовательский сеанс.
