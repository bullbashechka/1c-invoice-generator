# Этап 2: основа операций и восстановления

Состояние на 9 октября 2026: этап закрыт по решению заказчика с отказом от оставшихся проверок. Непроведённые сценарии сохраняют статус «не проверено» в протоколе и матрице сквозной приёмки; закрытие этапа не подтверждает их успешность. Допуск создания остаётся выключенным.

## Состав

Существующее расширение и UUID заимствованных объектов сохранены. Историческая EPF содержит браузерный переход и обработчик проведения с закрытием; эти части в новый REST-поток не переносятся. Старые сервисные регистры не мигрируют и не отправляют заявки.

- `Расш1_ЖурналОперацийБ24`: отдельная запись на UUID попытки; база, портал, заказ, инициатор, сеанс, начало UTC, неизменный JSON данных и срока, состояние, флаг возможной отправки, известный ID и версия связи.
- `Расш1_СостояниеЗаказовБ24`: текущая операция, версия связи и ID последней удалённой связи.
- `Расш1_СвязиЗаказовБ24`: прежний ключ заказа; добавлены портал, ссылка и снимок названия.
- `Расш1_АудитСвязейБ24`: отдельное событие изменения связи с сотрудником, временем и прежним/новым ID.
- `Расш1_УведомленияБ24`: сообщения инициатору и устойчивое подтверждение показа.
- `Расш1_ОперацииRESTБ24`: серверная логика; привилегированный доступ к собственным регистрам в ограниченных участках с восстановлением исходного режима.
- `Расш1_СервисRESTБ24`: клиентский контракт без секрета и тел REST-ответов. Кнопка и её штатное проведение остаются T51.

## Переходы

`Резерв → ОтправкаНачата → ЗадачаИзвестна → Завершена`.

Флаг возможной отправки фиксируется до HTTP. Потеря ответа переводит операцию в `Неизвестно`; восстановление вызывает только поиск по `=XML_ID`, никогда `tasks.task.add`. Маркер: `KA2:{OperationUUID}`, 40 символов; полный UUID операции, портал и UUID базы остаются в журнале. Поиск использует маркер из неизменяемого снимка. Ноль результатов означает продолжающуюся неизвестность, несколько — `Конфликт`. Фильтров по названию, проекту, ролям или времени нет. Уникальность XML_ID на стороне Б24 не предполагается.

Первый живой прогон выявил обрезание прежнего 77-символьного XML_ID до 50 символов на демопортале. Обрезанный маркер не используется для автоматической привязки; такая операция остаётся неизвестной до отдельной сверки программистом. Формат 40 символов проверяется отдельным живым прогоном, без повторной отправки старой операции.

Не запущенный резерв становится `НеОтправлена`, а не автоматической очередью. Явный `insufficient_scope` с HTTP 401 классифицируется как `ОтказAPI`; неоднозначные HTTP/JSON/ERROR_CORE остаются неизвестными. Новый клик после терминальной неотправки создаёт новую запись и новый срок.

ID задачи фиксируется отдельной транзакцией до записи связи. Завершение атомарно сохраняет связь, версию, аудит и уведомление. При конфликте первая связь сохраняется. Завершённую операцию нельзя использовать для восстановления удалённой связи.

Единые метод и ключ фонового задания защищают отправку и восстановление от параллельного исполнения. Обработчик ожидания клиента раз в пять секунд запускает короткий серверный опрос; сеть выполняется в фоне. Уведомления показываются без открытия окон и затем подтверждаются. Открытые формы получают оповещение об обновлении состояния.

## Допуск и резервные копии

Создание по умолчанию выключено: собственная настройка `stage2Enabled` должна иметь точное значение `true`. Изменять её должен программист в защищённом регистре, отдельно от поставляемых исходников. Выключение не удаляет журнал и не отменяет восстановление уже отправленных попыток. Настройка `rest` и её секрет остаются только в базе.

После восстановления старой копии базы оставить допуск выключенным, вручную сверить операции и связи с Б24, затем включить. Автоматического распознавания отката нет.

## Проверки

Жизненный цикл перехватывается в объектном модуле заказа: сравнение до записи, подготовка сообщения после штатного `ПриЗаписи` в той же транзакции. Отмена в этой КА определяется как отмена всех товарных строк либо статус «Закрыт» с отменёнными строками. Само закрытие выполненного заказа и снятие проведения отменой не считаются. Нужен отдельный живой прогон помощника закрытия и отказа/отката записи; проверка исходников не подтверждает пользовательское действие.

При подготовке REST локальная ошибка до вызова транспорта означает достоверную неотправку. После вызова транспорта исключение означает неизвестность. Приёмка результата поиска дополнительно перечитывает точный ID задачи и сравнивает XML_ID. Подтверждённый ID не теряется при недоступности последующего чтения срока.

Для управляемого сбоя администратору КА Демо доступен серверный параметр `after-response`; рабочее фоновое задание его не передаёт. Он отбрасывает только подтверждённый успешный ответ до записи ID; отказ или неотправка сохраняются обычным способом. Это проверка восстановления потерянного результата, а не подтверждение поведения при обрыве TCP.

Исходные Red на установленном расширении: отсутствуют `РазобратьСоздание`, `СрокЗадачиИстек` и регистр устойчивого журнала. Прогон резерва до появления модуля завершился неподтверждённым ответом Toolkit; он не считается Red. Дополнительные воспроизведённые дефекты: новый контракт маркера не проходит на старом формате; поиск известной задачи возвращает неизвестность из-за конфликта переменной `Задачи` с глобальным объектом 1С. Штатная синтаксическая проверка этот конфликт не обнаружила; проверка выполняется на установленном полном модуле.

Новые BSL-контракты проверяют установленный полный модуль и метаданные; резерв выполняется в транзакции с откатом и без HTTP. Не считать эти проверки подтверждением потери настоящего REST-ответа, конкурентных сеансов, прав сотрудника или пользовательского уведомления. Фактические результаты загрузки, CFE и живых прогонов записываются в `docs/stage-1-prototypes.md`.
