# Диагностика и worker демопрототипа Б24

Каталог содержит страницу чтения интерфейса Б24, тест регистрации диагностической вкладки и исходники worker. Последнее подтверждённое чтение установленного пакета приложения №80 показывало `enabled=true`; в исходниках `worker-config.js` очередь остаётся выключенной. Сквозной прогон с этим пакетом не завершён.

## Текущее состояние

- `index.html`, `probe.js`, `bind.js` — диагностика scope и placements; привязка диагностической вкладки ограничивается тестовой группой.
- `navigation.js` — построение пути стандартной формы через `BX24.openPath`; это не доказывает сохранение параметров или работу из 1С.
- `worker.html`, `background_worker.js`, `worker-config.js` — прототип очереди через личные REST-хранилища `Q_<userId>` и `R_<userId>`. Service-origin и передача браузерного токена отсутствуют.
- Worker проверяет iframe, `BXDesktopSystem.SetActiveTab`, `BXDesktopSystem.IsActiveTab`, `BXDesktopWindow.ExecuteCommand` и `BXDesktopWindow.GetProperty`; использует постоянный `workplaceId`, отдельный `instanceId` и только адресованное ему разрешение. После активации он вызывает `BX24.openPath`, затем не дольше двух секунд проверяет активную вкладку и положение окна. Причины SDK, активации и закрытия передаются только кодами из фиксированного списка.
- В актуальных исходниках главная страница читает профиль рабочего места даже при выключенной очереди. `readWorkplaceProfile` возвращает `baseId`, `initiatorId` из `user.current` и постоянный `workplaceId`; worker использует ту же функцию и ключ локального хранения. Текущий исходник ещё не размещён на портале, доступность новых команд в скрытом фрейме не проверена.
- Конфигурация остаётся выключенной: `enabled=false`, `standardCardVerified=false`.

5 октября 2026 года подтверждено: запись интеграции №90 ведёт к установленному приложению №80. По ранее полученному подтверждению добавлены `user_brief` и `entity`, сохранены `task` и `placement`. Прежний пакет диагностики и выключенного worker размещён в этом приложении. Регистрация worker с USER_ID и errorHandlerUrl подтверждена чтением; скрытый фрейм в десктопном клиенте показал desktop_detected. Стандартная карточка сохранила точный тег демозадачи №9926 после ручного изменения текста. В продолжении прогона получена авторизация текущего пользователя 30 и проверены его личные каналы `Q_30/R_30` с правами `U30:X`. Полный обмен ещё не проверен.

## Исторические диагностические результаты

2 октября был выполнен диагностический прогон страницы приложения: после повторной загрузки чтение scope/placements завершилось, список placements содержал точки задач, основной интерфейс не показывал команд или событий. Это не доказывает отсутствие команд в контексте карточки задачи.

В историческом прогоне зарегистрирована вкладка `TASK_VIEW_TAB` только для проекта «Гем платежи демо» (ID 36); повторное чтение подтвердило привязку. Вкладка отсутствовала в новой несохранённой карточке задачи и не была проверена в сохранённой задаче. Задачи не создавались.

Прежний вывод об отсутствии приложения №80 был ошибочным: ID записи интеграции и ID установленного приложения различаются. Проверка 5 октября подтвердила связь №90 → №80; другие интеграции не менялись.

## Локальные проверки

Из корня репозитория:

```powershell
node --test tests/stage1/*.cjs
```

Тесты подтверждают построение URL, отказ обычному браузеру, фильтрацию сообщений `entity`, ID рабочего места/окна, отсутствие открытия без точного разрешения, heartbeat и перевод закрытия в неизвестный исход. SDK и REST в автоматизированных проверках подставляются; портал, desktop bridge, сохранение метки и возврат ID ими не подтверждаются.

## Привязка сотрудника и компьютера

После размещения актуального пакета откройте приложение №80 в десктопном Б24 и нажмите «Прочитать профиль рабочего места». Чтение не включает очередь, не создаёт задачу и не передаёт OAuth-токены. `initiatorId` и `workplaceId` из результата используются в настройке расширения `profile|<UUID пользователя 1С>|<ИмяКомпьютера>`; `baseId` должен совпадать с настройками расширения и службы. Значения не определять по имени сотрудника или адресу `user/30`.

Профиль привязан к хранилищу приложения в этом десктопном клиенте. Очистка хранилища или изменение домена размещения пакета требует повторной настройки привязки. Чтение профиля само по себе не проверяет права каналов Q_/R_ и возврат результата.

## Локальный файл доступа службы

`oauth_export.js` и кнопка «Сохранить файл доступа службы» читают текущую авторизацию SDK после проверки нативной среды и профиля. Файл содержит access/refresh токены, портал и профиль; срок SDK переводится из миллисекунд в секунды. Файл сохраняется локально, токены не отображаются в интерфейсе и не помещаются в localStorage, entity или пакет приложения. Файл не отправлять в чат. Для службы его объединяют с реквизитами существующего приложения в отдельном закрытом файле настроек; исходники и CFE секретов не содержат.

В живом прогоне функция временно выполнена в уже установленном приложении №80 и сохранила локальный файл без вывода значений токенов. REST `user.current` подтвердил пользователя 30; регистрация worker перечитана. Пакет с новой кнопкой ещё не загружен. В исходниках также исправлен вызов остановки выключенного worker при `pagehide` и добавлена отсутствовавшая страница `worker-error.html`; исправление ещё не подтверждено после размещения на портале.

## Диагностика 5 октября

`correlated_probe.js` открывает стандартную карточку только в нативной среде, передаёт название/проект/точный тег и перечитывает найденные задачи. Описание вводится вручную. Пустой поиск означает неизвестный результат; несколько точных совпадений — конфликт. Поддержаны страницы SDK и фактические объекты TAGS `id/title`.

`worker_probe.js` регистрирует worker текущего пользователя и сверяет сохранённые значения; чужая конфликтующая регистрация не заменяется. `worker.html` сохраняет диагностическое наблюдение среды даже при выключенной очереди. Обычная браузерная страница отказала открытию; отрицательный прогон скрытого браузерного worker пока не завершён.

Актуальные живые результаты и ограничения: [B24-14/B24-15](../../docs/stage-1-prototypes.md#продолжение-5-октября-2026-года).

## Нативная активация — 5 октября 2026 года

`background_worker.js` теперь вызывает `SetActiveTab()` и `ExecuteCommand('show.active')` после подтверждённого разрешения. Затем вызывает `BX24.openPath` и проверяет `IsActiveTab()` вместе с `GetProperty('isForeground')` максимум две секунды. Отсутствующий мост, исключения SDK, ошибка маршрута, timeout и закрытие карточки различаются; свободный текст ошибок и секреты в диагностическое сообщение не попадают. Сообщение `opened` означает отправку команды, не подтверждение загрузки формы.

Подготовлен локальный диагностический ZIP `diagnostics-current-account-oct5.zip` с 11 файлами, без секретов и с выключенной очередью; SHA-256 `52d6fb816b25f2fc3385f3fef37a34a992060d05ca146d6f8284259e09893831`. Он пока не загружен в Б24. Новый bridge, живое открытие карточки и возврат ссылки этим исходником не подтверждены.

## Браузерная проба через приложение — 6 октября

Код и локальный пакет подготовлены. Загрузка в приложение №80 отклонена автоматической проверкой разрешений до явного согласия на отправку ZIP порталу; живая проба не выполнена.

`browser_probe.js` и отдельная кнопка главной страницы проверяют `BX24.openPath` в обычном браузере. Проба доступна после чтения SDK в основном контексте `DEFAULT` с правом `task`. Она открывает только новую стандартную форму проекта «Гем платежи демо» (36) с синтетическим названием и собственной меткой `КА-browser-<UUID>`. После отправки запроса повторное открытие той же пробой запрещено, включая закрытие с неизвестным результатом. Для нового независимого прогона страницу обновляют.

Проверьте название «Проверка контрагента & филиал №1.» и точный тег из отчёта, затем закройте форму без сохранения. Описание, участников и срок проба не подставляет; сохранение задачи не выполняет. `request_sent` обозначает отправку команды, а `slider_closed_result_unknown` — закрытие без доказательства создания или отмены. Проба не регистрирует worker, не включает очередь и не записывает связь в 1С. Нативные ограничения остальных команд сохранены.

Тесты `test_browser_probe.cjs` проверяют эти ограничения и поведение кнопки главной страницы с подставленным SDK. Реальное заполнение, подключение к «Провести и закрыть» и возврат ID требуют отдельного живого прогона. Фактические результаты — в [протоколе](../../docs/stage-1-prototypes.md#браузерная-проверка--6-октября-2026-года).

## Отказ загрузки SDK — 6 октября

Версия страницы `browser-sdk-guard-20261006` записывает в отчёт `build` и блок `sdk`: публичный адрес библиотеки, состояние `load` (`loaded`, `failed`, `pending` или `unknown`) и наличие функции `init`. `loaded` подтверждает событие загрузки скрипта, но не успешную инициализацию или доступ к порталу. `failed` сообщает ошибку загрузки без предположения о её причине; HTTP-код, блокировщик и настройки Firefox этим не определяются.

Пока чтение SDK не завершено, внешние команды остаются выключенными и их обработчики не назначаются. Локальное чтение ранее записанного наблюдения worker остаётся доступным. Ошибка открытия нативной пробы возвращается отдельным безопасным кодом; синхронный результат SDK не затирается состоянием отправки запроса.

`test_app_initialization.cjs` запускает реальные браузерные исходники страницы с подставленным SDK и проверяет отказ библиотеки в браузерном/нативном окружении, тайм-аут, исключение инициализации, события загрузки, локальное чтение и ошибки навигации. Эти проверки не заменяют повторный прогон размещённого пакета в браузере пользователя.
