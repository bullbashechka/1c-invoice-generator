# Демопрототип службы обмена 1С → Б24

Служба хранит операции в SQLite и передаёт сообщения через личные хранилища Б24 `Q_<userId>` и `R_<userId>`. Фоновый worker обращается только к REST Б24; прямой API службы из браузера, `ONTASKADD` и автоматическое создание задачи не используются. Сотрудник вручную сохраняет стандартную карточку.

## Текущее состояние

- `operation_store.py`: SQLite, WAL, `synchronous=FULL`, транзакции `BEGIN IMMEDIATE`, уникальность операции, заказа и ID задачи, outbox/inbox и блокировки активной 1С-сессии.
- `bitrix_entities.py`: REST-клиент `entity`/`placement`, создание личных каналов, права без `AU`, проверка персонального `PAGE_BACKGROUND_WORKER`; повтор удалённой публикации сначала сверяет уже записанное сообщение.
- `entity_sync.py`: обработка ответов worker, атомарная выдача разрешения одному окну, повтор публикации, поиск по точному тегу и перечитывание задачи перед принятием ID. Перед настройкой и стартовой проверкой регистрации сверяется принадлежность OAuth-токена техническому владельцу через `user.current`.
- `oauth_bootstrap.py` и `oauth_tokens.py`: одноразовый импорт OAuth-пары и атомарное обновление access/refresh токенов во внешнем локальном файле.
- `operation_http.py`: локальный HTTP API адаптера расширения 1С, включая heartbeat, свежую проверку заказа и подтверждение результата. Исходники адаптера включены в промежуточный CFE; настройки и токены задаются данными демобазы, обмен выключен.
- `src/stage-1-diagnostics/`: worker по умолчанию выключен (`enabled=false`, `standardCardVerified=false`). Исходник требует в скрытом фрейме `BXDesktopSystem.SetActiveTab`, `BXDesktopSystem.IsActiveTab`, `BXDesktopWindow.ExecuteCommand` и `BXDesktopWindow.GetProperty`; при разрешении вызывает `SetActiveTab()` и `show.active`, затем `BX24.openPath`, после чего не дольше двух секунд проверяет активную вкладку и foreground. Этот новый набор API ещё не проверен в установленном скрытом фрейме: раньше подтверждалась только общая нативная среда старого пакета.

Эти компоненты проходят локальные тесты, но сквозной обмен с расширением 1С и порталом ещё не выполнен. 5 октября приложение №80 найдено через запись интеграции №90; его права дополнены до `task`, `placement`, `user_brief`, `entity`. Стандартная десктопная карточка сохранила точный тег демозадачи №9926; полный обмен заказа и результата не выполнен. См. [протокол этапа 1](../../docs/stage-1-prototypes.md).

## Локальная проверка

Из корня репозитория в PowerShell:

```powershell
python -m unittest discover -s tests/stage1 -p 'test_*.py' -v
node --test tests/stage1/*.cjs
```

Автотесты используют настоящие SQLite, HTTP-сокеты и процессы там, где это возможно; ответы REST Б24 подставляются. Они не подтверждают права реальных сотрудников, доступность `entity`, открытие карточки в десктопном Б24 или работу расширения 1С.

## Секреты и запуск

Настройки службы размещаются вне исходников и CFE, например в исключённом из Git `.local/stage-1/http-settings.json`. Ключи клиента разных баз и ключ результата должны быть независимыми случайными строками не короче 32 символов. OAuth-файл хранить отдельно от исходников с ACL учётной записи, запускающей службу.

Первую OAuth-пару импортировать интерактивно один раз:

```powershell
python src/stage-1-service/oauth_bootstrap.py --path .local/stage-1/oauth-tokens.json
```

Команда не перезаписывает существующий файл; секрет и токены вводятся через скрытый ввод. Не передавать их аргументами командной строки, не помещать в логи или конфигурацию репозитория.

Пример формы настроек без рабочих значений:

```json
{
  "database": "operations.sqlite",
  "port": 6014,
  "bindHost": "127.0.0.1",
  "clientTokens": {"base-id": "REPLACE_WITH_DISTINCT_RANDOM_CLIENT_TOKEN"},
  "resultToken": "REPLACE_WITH_DISTINCT_RANDOM_RESULT_TOKEN",
  "bitrixEntity": {
    "portal": "https://portal.example",
    "baseId": "base-id",
    "employeeIds": ["123"],
    "technicalOwnerUserId": "456",
    "oauthTokenFile": "oauth-tokens.json",
    "workerHandlerUrl": "https://static.example/worker.html",
    "errorHandlerUrl": "https://static.example/error.html",
    "provisionOnStartup": false,
    "pollSeconds": 5,
    "reconciliationSeconds": 10
  }
}
```

Значения `employeeIds`, `technicalOwnerUserId`, портал и URL пакета должны быть подтверждены для целевого портала. `provisionOnStartup=true` меняет состояние Б24: создаёт хранилища/поля и при необходимости регистрирует персональный worker. До нахождения подтверждённого приложения службы запуск с включённым provision запрещён.

Служба по умолчанию слушает только loopback. Нелокальный `bindHost` требует явного TLS-сертификата и закрытого ключа; минимальная версия — TLS 1.2. Запуск:

```powershell
python -X utf8 src/stage-1-service/operation_http.py --config .local/stage-1/http-settings.json
```

## HTTP-контракт для расширения 1С

Все запросы используют `Authorization: Bearer <clientToken>`, кроме `POST /v1/results`, который требует отдельный `resultToken`. POST передаёт JSON с `Content-Length`; максимальный размер тела — 65 536 байт. Чужая база или роль даёт 403, неизвестная операция — 404, конфликт контекста — 409. Пути, тела и токены не включаются в диагностические сообщения.

| Метод и путь | Назначение |
| --- | --- |
| `POST /v1/operations` | Начать операцию или вернуть точный повтор |
| `GET /v1/operations/{operationId}` | Прочитать состояние своей операции |
| `POST /v1/task-requests` | Сохранить неизменяемую заявку, адресованную инициатору/рабочему месту/сеансу |
| `GET /v1/task-requests/{operationId}` | Прочитать состояние доставки заявки |
| `POST /v1/1c/heartbeat` | Продлить lease активного сеанса 1С на 30 секунд |
| `POST /v1/1c/checks` | Получить проверки сохранённого заказа для текущего сеанса |
| `POST /v1/1c/validate` | Ответить на свежую адресованную проверку заказа |
| `GET /v1/results` | Получить результаты, ещё не подтверждённые расширением |
| `POST /v1/acknowledgments` | Подтвердить результат после фиксации связи в регистре 1С |
| `POST /v1/unknown` | Сохранить неизвестный исход без разрешения новой операции |
| `POST /v1/results` | Внешняя передача проверенного результата; в worker-сценарии не используется |

Личное хранилище `Q_<userId>` содержит заявки и разрешения на открытие; `R_<userId>` — сообщения worker. При разных учётных записях у сотрудника чтение `Q_` и запись `R_`, у владельца OAuth службы управление. Служба может использовать OAuth самого инициатора: тогда этот пользователь имеет `X` в обоих собственных каналах. При совпадении ролей право `X` не заменяется на `R/W`; общий `AU` не выдаётся. Перед настройкой по-прежнему проверяется фактический владелец OAuth через `user.current`. SQLite остаётся источником состояния и единственным владельцем блокировок.

Сервис синхронизирует entity каждые 5 секунд, сверяет незавершённые задачи каждые 10 секунд. Worker опрашивает очередь каждые 5 секунд и отправляет heartbeat карточки каждые 10 секунд. После принятого `opening` удержание операции составляет 90 секунд; `opened` и каждый heartbeat продлевают его ещё на 90 секунд только для того же действующего владельца. Просроченный lease переводит доставку в `unknown`; heartbeat не восстанавливает его. Короткий срок одноразового разрешения на открытие не продлевается. Точный тег `КА-<operationId>` используется для поиска; найденная задача перечитывается. Пустой результат оставляет операцию неизвестной, несколько совпадений переводят её в конфликт. Закрытие слайдера не подтверждает ни отмену, ни создание.

В службе есть локальные Red/Green-тесты outbox, конфликтов, повторов, OAuth-ротации, HTTP-контракта и корреляции. 5 октября OAuth текущего инициатора 30 проверен через настоящий REST; созданы и перечитаны `Q_30/R_30` с правами `U30:X`. Отдельная техническая учётная запись для этого демопрогона не требуется. Обновление OAuth после истечения срока, публикация сообщений, запись ID/ссылки из 1С и права разных сотрудников пока не подтверждены. Регистрация worker, общая нативная среда старого скрытого фрейма и сохранение точного тега подтверждены диагностическими прогонами 5 октября; доступность новых команд активации и сквозной обмен не проверены. Worker исходного пакета выключен.
