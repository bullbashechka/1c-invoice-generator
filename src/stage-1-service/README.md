# Прототип устойчивого журнала операций

`operation_store.py` — локальная проверка хранения минимального контракта обмена. Использует стандартный `sqlite3`, WAL, `synchronous=FULL` и транзакции `BEGIN IMMEDIATE`. Одна база журнала обслуживает один настроенный портал: уникальность `taskId` действует для всего журнала, уникальность заказа — для пары `baseId`/`orderId`.

Состояния: `pending` → `unknown` либо `created` → `acknowledged`. Отмена без результата допускается только при явно подтверждённом отсутствии задачи. Повторный результат не меняет исходную связь; конфликт отклоняется. Полученный результат остаётся доступен для доставки до точного подтверждения сохранения связи в 1С. Подтверждение должен отправлять адаптер после успешной фиксации записи, а не до неё.

Это компонентный прототип. HTTP-транспорт описан ниже; обработчик событий Б24, открытие формы, опрос из расширения, аудит ручной замены связи, установка службы и размещение ещё не реализованы или не согласованы. Флаг `absence_confirmed` представляет уже выполненную проверку адаптера; сам журнал не устанавливает факт отсутствия задачи. Его нельзя считать доказательством отмены стандартной формы Б24.

Проверка из корня проекта:

```powershell
python -m unittest discover -s tests/stage1 -p 'test_operation_store.py' -v
```

Проверено на Python 3.13: десять тестов, включая запись результата отдельным процессом, повторную доставку после подтверждения, неправильные идентификаторы и конкурентные попытки создания/привязки. Используется настоящая SQLite во временном каталоге, без моков внешних систем. Это не подтверждает сквозной возврат из Б24, перезапуск постоянно работающего сервиса или норматив 60 секунд.

Для исходных шести требований зафиксирован Red на минимальном незавершённом интерфейсе (`NotImplementedError`), затем Green после реализации. Четыре дополнительных проверки ошибок и конкуренции прошли на готовом компоненте; отдельного исходного сбоя для них не заявляется. Рефакторинг после Green не требовался.

## HTTP-транспорт прототипа

`operation_http.py` запускает отдельный процесс, доступный только по `127.0.0.1`. Основа — стандартный `http.server`; это локальный стенд для проверки контракта, не сервер для сетевой эксплуатации. Подключение сотрудников с других компьютеров, HTTPS, размещение и установка службы требуют отдельной реализации после T10.

Настройки хранятся в исключённой из Git `.local/`, не в командной строке:

```json
{
  "database": "operations.sqlite",
  "port": 6014,
  "clientTokens": {"base-id": "REPLACE_WITH_DISTINCT_RANDOM_CLIENT_TOKEN"},
  "resultToken": "REPLACE_WITH_DISTINCT_RANDOM_RESULT_TOKEN"
}
```

Оба значения — независимые случайные секреты, созданные локально; пример нельзя использовать как готовые ключи. Относительный путь SQLite разрешается относительно файла настроек. Секреты не выводятся при запуске; строка готовности содержит только адрес и порт. Идентификаторы — 1–128 символов `A–Z`, `a–z`, `0–9`, `_`, `-`; UUID допустимы. Все запросы передают `Authorization: Bearer <ключ>`; POST также требует `Content-Type: application/json` и `Content-Length`. Размер тела ограничен 4096 байтами; повторяющиеся ключи JSON отклоняются. CORS не включён.

| Метод и путь | Право и результат |
| --- | --- |
| `POST /v1/operations` | Ключ своей базы; `baseId`, `orderId`, `operationId`; начать или прочитать точный повтор попытки |
| `GET /v1/operations/{operationId}` | Ключ своей базы; состояние своей операции; чужая или отсутствующая операция даёт 404 |
| `POST /v1/unknown` | Ключ своей базы; тот же контекст; зафиксировать неизвестный результат без разрешения новой попытки |
| `POST /v1/results` | Только отдельный ключ адаптера результата; контекст и положительный целочисленный `taskId`; сохранить результат или точный повтор |
| `GET /v1/results` | Ключ своей базы; `results` с ещё не подтверждёнными результатами этой базы |
| `POST /v1/acknowledgments` | Ключ своей базы; точные контекст и `taskId`; подтвердить уже записанную связь |

Ключ адаптера не выдаётся клиенту 1С. Адаптер должен сначала достоверно установить результат создания в Б24; HTTP-приём сам этот факт не проверяет. Клиент подтверждает результат только после фиксации связи в регистре. Через HTTP отмена не предоставляется: тайм-аут, пустая очередь и закрытие окна не доказывают отсутствие задачи. Ошибки: 401 — неверный ключ, 403 — чужая база/роль, 409 — конфликт; результат остаётся в журнале до точного подтверждения. Пути, тела запросов и ключи не записываются в диагностический вывод.

Запуск из корня проекта с подготовленными локальными настройками:

```powershell
python -X utf8 src/stage-1-service/operation_http.py --config .local/stage-1/http-settings.json
python -X utf8 -m unittest discover -s tests/stage1 -p 'test_operation*.py' -v
```

Проверены 17 тестов: 10 журнала и 7 HTTP. Первые пять HTTP-сценариев дали Red (`501` вместо требуемого ответа), затем Green. Дополнительные проверки некорректных запросов и ключей пройдены без отдельного исходного сбоя. Тесты используют настоящие HTTP-сокеты, SQLite и новый процесс сервера. Потеря тела ответа проверяется закрытием соединения после заголовков; аварийное завершение до фиксации транзакции этим не проверено.

В «КА Демо» отдельно выполнен [сценарий получения](../../tests/stage1/http_receive_contract.bsl): `HTTPСоединение` получило синтетический результат `base-a/order-1/op-1/taskId=42` и проверило все поля. Ответ — `STAGE1_HTTP_RECEIVE_GREEN`; записи в документ/регистр и подтверждения результата не было, результат остался доступен для доставки. Прогон выполнен через MCP как инструмент проверки, не через работающий обработчик расширения. Реальная задача Б24, автоматический опрос, запись связи и оба срока 60 секунд остаются непроверенными.
