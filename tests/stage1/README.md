# Проверки прототипов этапа 1

## Журнал операций

Из корня репозитория:

```powershell
python -m unittest discover -s tests/stage1 -p 'test_operation_store.py' -v
```

Используются настоящая SQLite, параллельные транзакции и отдельный процесс. Эти проверки подтверждают контракт компонента хранения. Б24, расширение, постоянно работающий сервис и сроки сквозного восстановления они не проверяют.

## Регистр расширения в 1С

`register_contract.bsl` выполняется только в «КА Демо» с установленным прототипом из `src/stage-1-prototype`. Через Toolkit вызвать `execute_code`, передав содержимое файла как `code` и `execution_context: "server"`. Подтверждение записи выполняет пользователь; автоматическое разрешение не требуется.

Прогон создаёт две синтетические ссылки, записывает только собственный регистр и удаляет собственные тестовые строки. Документы и задачи Б24 не создаются. Проверяются точная повторная доставка, занятая задача, повторная операция для другой пары и сохранность исходной связи. Успешный ответ — `STAGE1_REGISTER_CONTRACT_GREEN`.

До исправления проверки операции этот же сценарий дал `STAGE1_RED: операция принята для другого заказа и задачи`; после исправления в новом сеансе прошёл. Конкурирующие сеансы, ручная замена, аудит и доставка реального результата Б24 остаются отдельными проверками. Подробности и версии — в [протоколе](../../docs/stage-1-prototypes.md).

`register_batch_operation.bsl` проверяет две связи с одной операцией внутри одного пакета. Выполнять в том же серверном контексте с подтверждением пользователя. Используются синтетические ссылки и незанятые тестовые ID; `Записать(Ложь)` не заменяет существующие строки. Транзакция всегда откатывается. Ожидается `STAGE1_BATCH_OPERATION_GREEN`; отсутствие отказа даёт `STAGE1_RED: один пакет принял две связи с одинаковой операцией`. Исходный Red получен в демобазе. После исправления в новом сеансе получен `STAGE1_BATCH_OPERATION_GREEN`; основной контракт регистра тоже прошёл. Отдельное чтение подтвердило пустой регистр. Этот сценарий не проверяет конкуренцию разных сеансов.

## Конкурирующие сеансы 1С

`run_register_concurrency.py` использует два реальных экземпляра Toolkit в разных сеансах одной «КА Демо», на отдельных loopback-портах. До записи проверяет версию КА, пустой собственный регистр, одинаковый SHA256 строки подключения и разные номера сеансов/соединений. Путь подключения не возвращается и не записывается. Fingerprint должен совпасть с отдельным локальным доказательством заранее проверенной демобазы; одинаковой версии конфигурации недостаточно.

1. Открыть существующую «КА Демо» в двух независимых сеансах. Запустить имеющуюся обработку Toolkit в каждом на портах 6003 и 6004. Аутентификацию и подтверждения операций выполняет пользователь; настройки безопасности не отключать.
2. В заранее проверенном сеансе демобазы выполнить только чтение из константы `PROBE` Python-сценария. Сохранить исходный JSON-RPC-ответ локально как `{"response": <ответ>}`. На текущем стенде такое доказательство находится в исключённом из Git `.local/stage-1/concurrency-session-current-private.json`.
3. Из корня проекта выполнить:

```powershell
python -X utf8 tests/stage1/run_register_concurrency.py --ports 6003 6004 --demo-proof .local/stage-1/concurrency-session-current-private.json
```

Параметр `--conflict task` (по умолчанию) задаёт общую задачу при разных заказах и операциях; `--conflict order` — общий заказ при разных задачах и операциях; `--conflict operation` — общую операцию при разных заказах и задачах. В каждой паре общий ровно один ключ.

Первая BSL-процедура записывает синтетическую связь внутри открытой транзакции и ждёт HTTP-барьер. Вторая процедура из другого сеанса пытается записать конфликтующую пару. После наблюдаемого перекрытия попыток первая транзакция фиксируется. Ожидаются конфликт второй записи, сохранность первой связи и ноль тестовых строк после очистки. Проверяются точные номера сеансов в ответах. Очистка допускает только точные тройки заказа, задачи и операции текущего прогона. Документы и задачи Б24 не создаются.

Барьер работает только по `127.0.0.1` на временном порту; ожидание первой транзакции ограничено. Проверка и очистка точных строк выполняются под блокировкой регистра. При потере ответа результат считается неизвестным: автоматическая очистка откладывается, отчёт содержит `cleanupRequired=true`. До повторного прогона установить завершение обеих операций и проверить собственные UUID/ID из локального отчёта; тайм-аут клиента сам по себе не подтверждает остановку кода 1С. Восстановление после обрыва процесса этим сценарием не автоматизировано.

Успех допустим только при `STAGE1_REGISTER_CONCURRENCY_GREEN`, `overlapObserved=true`, ожидаемых ответах обоих сеансов и `firstLinkPreserved=true`, `testRowsRemaining=0`. `py_compile`, недоступный второй порт и отказ предварительной проверки не засчитываются как результат конкуренции.

На 1 октября получен только `preflight_failed` до записей: второй MCP-порт отсутствовал. **2 октября сценарий прошёл в живой 1С** на двух разных сеансах одной КА 2.4.5.18: получены все указанные признаки успеха, последующее чтение из обоих сеансов подтвердило пустой регистр. Первая попытка закончилась неизвестным ответом; после позднего разрешения код откатился из-за недоступного барьера. Перед повтором проверены журнал Toolkit, отсутствие ожидающих подтверждений и пустой регистр. Подробности — [KA-08](../../docs/stage-1-prototypes.md#ka-08--конфликт-одной-задачи-в-двух-сеансах-выполнено-2-октября).

После добавления переключателя случаев и изменения очистки 2 октября вживую прошли `--conflict order`, `--conflict operation` и повтор `--conflict task`: во всех трёх наблюдалось перекрытие, ожидаемые ответы обоих сеансов, сохранность первой связи и ноль строк после очистки. Итоговое чтение обоих сеансов подтвердило ноль строк и ожидающих запросов. Предыдущие попытки общего заказа закончились тайм-аутами подтверждений; они восстановлены и не засчитываются как проверка конфликта. Подробности — [KA-09](../../docs/stage-1-prototypes.md#ka-09--дополнительные-конкурентные-случаи-выполнено-2-октября). Реализация регистра не менялась; Red дефекта и новый цикл исправления не заявляются.

Первый запрос разрешить в течение 60 секунд после запуска координатора; затем второй — в течение 15 секунд после появления, затем очистку в первом сеансе. Первая транзакция удерживается не более 25 секунд. Просроченный запрос отклонить; не разрешать его после остановки координатора.

Генератор тестовых пар проверяется без MCP:

```powershell
python -X utf8 -m unittest discover -s tests/stage1 -p 'test_concurrency_attempts.py' -v
```

Перед реализацией генератора три проверки допустимых случаев падали на `NotImplementedError`, отказ неизвестного случая проходил. После реализации прошли все четыре. Это TDD генератора сценария, не проверка атомарности регистра. Полный набор `test_*.py` прошёл: 21 тест.

## Штатное проведение с закрытием

Воспроизводимый ручной прогон [KA-05](../../docs/stage-1-prototypes.md#ka-05--успешное-провести-и-закрыть-red-и-green) выполняется на отдельном собственном заказе только в «КА Демо». Сохранить фактический UUID документа локально; не искать его по свободному комментарию. Запускать штатные кнопки формы, а не подменять их прямой записью объекта или вызовом диагностического обработчика.

Через Toolkit `get_event_log` читать событие `STAGE1_POST_CLOSE` с `object_description` точной ссылки заказа. Сравнивать количество до и после каждой команды. После обычной записи, проведения без закрытия, штатного отказа по оплате и успешного закрытия с существующей тестовой связью оно не изменяется. После успешного «Провести и закрыть» без связи увеличивается на один; форма закрывается, серверное чтение подтверждает проведение. Временную связь записывать и очищать отдельно с подтверждением пользователя, проверяя точный ID и операцию. После прогона снять с проведения и пометить на удаление только собственный заказ; факт очистки проверить отдельно.

Red до добавления обработчика: успешное штатное закрытие, но событие отсутствует. Green после применения расширения в новом сеансе: одно событие успешного закрытия и отсутствие добавлений в остальных проверенных ветках. Это подтверждает точку подключения; Б24, сетевой отказ и восстановление связи не проверяет. Автоматизации пользовательских команд в этом наборе нет.
