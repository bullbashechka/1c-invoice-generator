# Проверки прототипов этапа 1

## Этап 2 — устойчивые операции

Выполнять BSL-контракты на сервере **установленного** расширения в новом сеансе «КА Демо». Перед записью сверять fingerprint базы с разрешённым локальным профилем. Разрешение диагностической записи в Toolkit не является включением REST-создания в продукте.

| Файл | Что проверяет | Изменения |
| --- | --- | --- |
| `rest_create_response_contract.bsl` | Только положительный ID подтверждает создание; пустой/неполный ответ и ERROR_CORE/5xx неизвестны | Нет сети и записи |
| `operation_metadata_contract.bsl` | Журнал по UUID попытки и необходимые устойчивые поля | Нет сети и записи |
| `rest_expired_deadline_contract.bsl` | Фактический срок, завершение задачи и ручной перенос срока | Нет сети и записи |
| `operation_reservation_contract.bsl` | Повтор сохраняет первый UUID, инициатора, снимок и срок | Регистры, полный откат, без HTTP |
| `operation_link_contract.bsl` | ID до связи, запрет ручной правки, завершение, удаление, поздний результат и подтверждение показа | Синтетический ID, полный откат, без HTTP |
| `operation_conflict_contract.bsl` | Два заказа с одним подтверждённым ID: первая связь сохраняется, вторая останавливается, поздний ответ не снимает конфликт | Синтетические ID, полный откат, без HTTP |
| `operation_not_sent_contract.bsl` | Неотправка не становится очередью; новый клик сохраняет историю; неизвестность блокирует только свой заказ | Полный откат, без HTTP |
| `operation_lifecycle_contract.bsl` | Перехват успешной записи собственной копии заказа, отсутствие повтора предупреждения, отмена/пометка с сохранением связи | Собственная копия, синтетический ID, полный откат, без HTTP |
| `operation_rest_response_loss.bsl` | Управляемая потеря настоящего ответа до записи ID, точный XML_ID + get, восстановление той же задачи и отсутствие дубля | **Одна реальная задача и связь сохраняются** |
| `operation_restart_recovery_contract.bsl` | После отдельного сбоя и нового входа: единственная задача по полному маркеру, сохранённая связь, название/описание/роли из снимка и выключенный допуск | Только чтение Б24 и регистров; требует метку `ДиагностическийСеанс` |

`operation_rest_response_loss.bsl` требует явного `РазрешенЖивойПрогон = Истина`, администратора и подтверждённой демобазы. Не запускать автоматически, в рабочей базе или повторно после неподтверждённого ответа. Сначала найти уже сохранённую операцию и восстановить её. Прогон не изменяет и не проводит исходный заказ; временно включает допуск создания и выключает его при завершении/обработанном сбое. Аварийное завершение между этими действиями требует отдельной проверки допуска программистом.

Проверки с синтетическими ID подтверждают работу BSL/регистров и не подтверждают REST. Вызов уведомления и подтверждение его показа не заменяют визуальную приёмку сотрудником. Копия заказа не заменяет прогон штатного помощника закрытия. Конкуренция разных сотрудников проверяется отдельно. Восстановление после полного выхода проверено для административного сеанса; это не подтверждает вход другого сотрудника или визуальный показ уведомления.

`test_extension_metadata.py` проверяет согласованность XML, ссылок конфигурации, UUID выгрузки и пространств имён типов; не эмулирует бизнес-логику.

## Новый REST-сценарий — BSL

`rest_module_contract.bsl` вызывает процедуры **полного установленного** `Расш1_RESTБ24Сервер`, без извлечения тел из исходников. Выполнять в серверном контексте нового сеанса после загрузки расширения. Проверяет JSON, отказ API, неверные настройки и номер задачи без сетевых вызовов и записи базы. Ожидается `REST_MODULE_CONTRACT_GREEN`; отдельно нужна штатная проверка конфигурации.

`rest_deadline_contract.bsl` вызывает установленный метод расчёта срока. Проверяет 18:59:59/19:00:00/19:00:01 UTC+5, полночь, выходной, месяц, год и високосный февраль на синтетических датах UTC. Часы компьютера и база не меняются. Ожидается `REST_DEADLINE_CONTRACT_GREEN`. Этот тест не подтверждает сохранение срока в операции или реальной задаче Б24.

`rest_settings_setup.bsl` — однократная административная настройка только КА Демо. Перед запуском задать `КаталогИсходников`; секрет читается из игнорируемого `.local/bitrix24-webhook.txt` и не возвращается в результат. После проверки параметров сценарий атомарно записывает `rest`, существующую строку не перезаписывает. Ожидается `REST_SETTINGS_SETUP_COMPLETE`. После тайм-аута не повторять запись до выяснения результата и закрытия просроченного запроса MCP.

`rest_settings_access_contract.bsl` выполнять под обычным сотрудником без административных прав и привилегированного режима. Проверяет эффективные права и фактический отказ прямого чтения секрета и записи настройки. Пробная запись всегда откатывается. Ожидается `REST_SETTINGS_ACCESS_CONTRACT_GREEN`. Запуск под администратором или директором с полными правами не заменяет эту проверку.

`legacy_disabled_contract.bsl` проверяет, что старые методы состояния, опроса и очереди безопасно выключены и не читают закрытые настройки. Ожидается `LEGACY_DISABLED_CONTRACT_GREEN`; получен в новом административном сеансе после загрузки. Административный прогон не подтверждает обычного сотрудника: под ним сценарий ещё требуется повторить.

`legacy_disabled_flags_contract.bsl` выполнять только администратором КА Демо. В транзакции задаёт прежний `enabled=true`, читает состояние прототипа и обязательно откатывает изменение до проверки. Старый флаг не должен включать исключённый сервис. Ожидается `LEGACY_DISABLED_FLAGS_CONTRACT_GREEN`; другие сервисные методы этим сценарием не вызываются.

`rest_background_start.bsl` запускает штатное фоновое чтение существующей задачи №10028 без ожидания завершения. Настройка `rest` уже должна быть записана; перед запуском подтвердить доступность задачи. `КаталогИсходников` нужен для локального диагностического журнала ID задания и адреса хранилища; секрет туда не входит. Хранилище привязано к отдельному UUID сеанса. `rest_background_result.bsl` запускать отдельным запросом в том же сеансе: ожидается `REST_BACKGROUND_CONTRACT_GREEN`. Если задание ещё выполняется, позднее повторять только чтение результата. Данные 1С/Б24 и связи не изменяются. Эти проверки подтверждают фоновый HTTPS без формы, но не заменяют проверку интерфейса при длительном запросе, закрытия открытой формы и устойчивого восстановления создания.

`saved_order_status_form_contract.bsl` выполняется в клиентском контексте Toolkit. Предварительно подготовить игнорируемый `.local/stage-1/saved-order-form-reference.json`: UUID сохранённого демозаказа в поле `Ссылка`, ожидаемые `Состояние`, `Ошибка`, `Номер` из серверного локального чтения `ДанныеЗаказа` для этого заказа с пустой ошибкой сеанса. Сценарий использует существующий серверный преобразователь ссылок Toolkit, открывает форму без записи/проведения и сравнивает отображённые поля. Историческая ошибка операции не очищается. Ожидается `SAVED_ORDER_FORM_CONTRACT_GREEN`; первоначальные ошибки преобразования ссылки в тонком клиенте не являются Red модуля продукта.

Длительное ожидание проверяется отдельно на Windows. После загрузки диагностического метода выполнить `python -X utf8 tests/stage1/rest_tls_wait_fixture.py`: временный слушатель занимает только свободный `127.0.0.1:443`, ждёт подключения не более 45 секунд и закрывает его через 16 секунд без завершения TLS. Не запускать при занятом порту. Это тестовая инфраструктура, не компонент поставки или Python-служба интеграции; байты и секреты не читаются. Настройка `rest` не меняется, проверка сертификатов остаётся включённой.

До запуска слушателя выполнить `rest_background_ui_prepare.bsl` в клиентском контексте Toolkit: он создаёт собственную чистую новую форму с отдельным UUID и запоминает фактический сеанс. После `TLS_FIXTURE_READY` в том же административном сеансе КА Демо запустить `rest_background_slow_start.bsl` на сервере. После `TLS_FIXTURE_CONNECTED` сразу выполнить `rest_background_ui_contract.bsl` на клиенте **того же MCP-порта**: он проверяет фактический сеанс, меняет видимость элемента подготовленной формы и закрывает только её, не сохраняя заказ. После завершения задания выполнить `rest_background_slow_result.bsl` на сервере того же сеанса. Последний сценарий проверяет длительность, совпадение сеанса/ID задания и выполнение клиентского сценария до завершения фона. Ожидается `REST_SLOW_BACKGROUND_UI_CONTRACT_GREEN`. Это контролируемое локальное ожидание TLS плюс реальное чтение задачи №10028, а не измерение задержки API Б24. Подготовка и UI-сценарий по отдельности прошли, совмещённый Green пока не получен. При отказе подключения или занятом порту тест не подтверждает отзывчивость; повторять запуск только после завершения прежнего задания.

`rest_settings_contract.bsl` выполняется с тем же `КаталогИсходников` в серверном контексте. Проверяет тело процедуры проверки настроек: HTTPS, совпадение портала, структуру вебхука, положительные целые ID, двух разных наблюдателей и корректные настройки. Используются синтетический домен `.invalid` и ключ `testkey`; сеть и записи базы отсутствуют. Ожидается `REST_SETTINGS_CONTRACT_GREEN`.

`rest_json_contract.bsl` выполнять через `execute_code` в серверном контексте КА Демо. Перед фрагментом задать `КаталогИсходников` — абсолютный путь к репозиторию. Прогон читает тело процедуры `Расш1_RESTБ24Сервер.ПрочитатьОтвет` из исходника и выполняет его в BSL, проверяя числовые ключи JSON, пустой/повреждённый ответ и отказ API. Ожидается `REST_JSON_CONTRACT_GREEN`. Данные базы и Б24 не меняются. Прогон не подтверждает компиляцию и применимость CFE.

`rest_recovery_contract.bsl` запускать так же, пока существует подготовленная демозадача. Нужны игнорируемые `.local/bitrix24-webhook.txt` и `.local/stage-1/rest-recovery-smoke.json` с полями исходной попытки, `XML_ID` и ожидаемым `taskId`. Прогон только читает Б24: ищет по метке, сверяет единственность, ID, название, участников, проект и срок. Ожидается `REST_RECOVERY_CONTRACT_GREEN`. Создание, удаление задач и запись связи не выполняются. Удалённая или недоступная задача не подтверждает неотправку. Этот сценарий проверяет компонент корреляции, а не автоматическое восстановление расширением.

## Регистр расширения в 1С

`register_contract.bsl` выполняется только в «КА Демо» с установленным прототипом из `src/stage-1-prototype`. Через Toolkit вызвать `execute_code`, передав содержимое файла как `code` и `execution_context: "server"`. Подтверждение записи выполняет пользователь; автоматическое разрешение не требуется.

Прогон создаёт две синтетические ссылки, записывает только собственный регистр и удаляет собственные тестовые строки. Документы и задачи Б24 не создаются. Проверяются точная повторная доставка, занятая задача, повторная операция для другой пары и сохранность исходной связи. Успешный ответ — `STAGE1_REGISTER_CONTRACT_GREEN`.

До исправления проверки операции этот же сценарий дал `STAGE1_RED: операция принята для другого заказа и задачи`; после исправления в новом сеансе прошёл. Конкурирующие сеансы, ручная замена, аудит и доставка реального результата Б24 остаются отдельными проверками. Подробности и версии — в [протоколе](../../docs/stage-1-prototypes.md).

`register_batch_operation.bsl` проверяет две связи с одной операцией внутри одного пакета. Выполнять в том же серверном контексте с подтверждением пользователя. Используются синтетические ссылки и незанятые тестовые ID; `Записать(Ложь)` не заменяет существующие строки. Транзакция всегда откатывается. Ожидается `STAGE1_BATCH_OPERATION_GREEN`; отсутствие отказа даёт `STAGE1_RED: один пакет принял две связи с одинаковой операцией`. Исходный Red получен в демобазе. После исправления в новом сеансе получен `STAGE1_BATCH_OPERATION_GREEN`; основной контракт регистра тоже прошёл. Отдельное чтение подтвердило пустой регистр. Этот сценарий не проверяет конкуренцию разных сеансов.

## Конкурирующие сеансы 1С

`run_register_concurrency.py` использует два реальных экземпляра Toolkit в разных сеансах одной «КА Демо», на отдельных loopback-портах. До записи проверяет версию КА, пустой собственный регистр, одинаковый SHA256 строки подключения и разные номера сеансов/соединений. Путь подключения не возвращается и не записывается. Fingerprint должен совпасть с отдельным локальным доказательством заранее проверенной демобазы; одинаковой версии конфигурации недостаточно.

1. Открыть существующую «КА Демо» в двух независимых сеансах. Запустить имеющуюся обработку Toolkit в каждом на портах 6003 и 6004. Аутентификацию и подтверждения операций выполняет пользователь; настройки безопасности не отключать.
2. В заранее проверенном сеансе демобазы выполнить только чтение из константы `PROBE` Python-сценария. Сохранить исходный JSON-RPC-ответ локально как `{"response": <ответ>}`. На текущем стенде такое доказательство находится в исключённом из Git `.local/stage-1/concurrency-session-current-private.json`.
3. Из корня проекта выполнить:

```powershell
python -X utf8 tests/stage1/run_register_concurrency.py --ports 6003 6004 --demo-proof .local/stage-1/concurrency-session-current-private.json
```

Параметр `--conflict task` (по умолчанию) задаёт общую задачу при разных заказах и операциях; `--conflict order` — общий заказ при разных задачах и операциях; `--conflict operation` — общую операцию при разных заказах и задачах. В каждой паре общий ровно один ключ.

Первая BSL-процедура записывает синтетическую связь внутри открытой транзакции и ждёт HTTP-барьер. Вторая процедура из другого сеанса пытается записать конфликтующую пару. После наблюдаемого перекрытия попыток первая транзакция фиксируется. Ожидаются конфликт второй записи, сохранность первой связи и ноль тестовых строк после очистки. Проверяются точные номера сеансов в ответах. Очистка допускает только точные тройки заказа, задачи и операции текущего прогона. Документы и задачи Б24 не создаются.

Барьер работает только по `127.0.0.1` на временном порту; ожидание первой транзакции ограничено. Проверка и очистка точных строк выполняются под блокировкой регистра. При потере ответа результат считается неизвестным: автоматическая очистка откладывается, отчёт содержит `cleanupRequired=true`. До повторного прогона установить завершение обеих операций и проверить собственные UUID/ID из локального отчёта; тайм-аут клиента сам по себе не подтверждает остановку кода 1С. Восстановление после обрыва процесса этим сценарием не автоматизировано.

Успех допустим только при `STAGE1_REGISTER_CONCURRENCY_GREEN`, `overlapObserved=true`, ожидаемых ответах обоих сеансов и `firstLinkPreserved=true`, `testRowsRemaining=0`. `py_compile`, недоступный второй порт и отказ предварительной проверки не засчитываются как результат конкуренции.

На 1 октября получен только `preflight_failed` до записей: второй MCP-порт отсутствовал. **2 октября сценарий прошёл в живой 1С** на двух разных сеансах одной КА 2.4.5.18: получены все указанные признаки успеха, последующее чтение из обоих сеансов подтвердило пустой регистр. Первая попытка закончилась неизвестным ответом; после позднего разрешения код откатился из-за недоступного барьера. Перед повтором проверены журнал Toolkit, отсутствие ожидающих подтверждений и пустой регистр. Подробности — [KA-08](../../docs/stage-1-prototypes.md#ka-08--конфликт-одной-задачи-в-двух-сеансах-выполнено-2-октября).

После добавления переключателя случаев и изменения очистки 2 октября вживую прошли `--conflict order`, `--conflict operation` и повтор `--conflict task`: во всех трёх наблюдалось перекрытие, ожидаемые ответы обоих сеансов, сохранность первой связи и ноль строк после очистки. Итоговое чтение обоих сеансов подтвердило ноль строк и ожидающих запросов. Предыдущие попытки общего заказа закончились тайм-аутами подтверждений; они восстановлены и не засчитываются как проверка конфликта. Подробности — [KA-09](../../docs/stage-1-prototypes.md#ka-09--дополнительные-конкурентные-случаи-выполнено-2-октября). Реализация регистра не менялась; Red дефекта и новый цикл исправления не заявляются.

## Состояние и адрес задачи в заказе

`order_status_contract.bsl` выполняется через Toolkit `execute_code` в серверном контексте установленного расширения в «КА Демо». Подтверждение операций выполняет пользователь. Используются синтетическая ссылка документа, собственные регистры и временная настройка портала внутри одной транзакции; транзакция откатывается и при успехе, и при ошибке. Документы не записываются и не проводятся, Б24 не вызывается.

Проверяются понятные состояния доставки, неизвестный результат, очистка произвольной диагностики от секретов, сохранность номера и адреса при ошибке доступа, отказ от адреса с userinfo и повреждённых настроек, пустая ссылка нового заказа. Ожидаемый результат — `ORDER_STATUS_CONTRACT_GREEN`. Исходный обработчик дал `ORDER_STATUS_RED: неизвестный результат показан техническим кодом`. Результат повторного живого прогона фиксируется отдельно в [протоколе](../../docs/stage-1-prototypes.md).

Контракт проверяет чтение данных расширения. Он не подтверждает доставку событий Б24, автоматический возврат реальной ссылки, переход в десктопное приложение или блокировку команд создания. Нативную форму заказа проверять дополнительно в новом сеансе после применения расширения.

`order_status_form_contract.bsl` выполняется в клиентском контексте Toolkit. Открывает новый незаписанный заказ и проверяет именно реквизиты управляемой формы: состояние «Заказ ещё не записан.», пустые номер, адрес и ошибка. Форма остаётся открытой для визуальной проверки; запись и проведение не вызываются. До исправления привязки динамических реквизитов получен `ORDER_FORM_RED: состояние нового заказа не заполнено в реквизите формы`; ожидаемый успешный результат — `ORDER_FORM_CONTRACT_GREEN`. Этот сценарий не проверяет сохранённый заказ или переход в Б24.

`run_order_status_delivery.py` проверяет публичный читатель состояний установленного расширения против временного HTTP-сервера на loopback. До записи сверяет fingerprint заранее подтверждённой демобазы, имя конфигурации и версию. BSL-сценарий создаёт синтетическую операцию и временные настройки внутри одной транзакции с откатом при успехе и ошибке; документы и Б24 не вызываются.

```powershell
python -X utf8 tests/stage1/run_order_status_delivery.py --demo-proof .local/stage-1/concurrency-session-current-private.json --output .local/stage-1/order-delivery-green-private.json
```

По умолчанию используется MCP-порт 6004. Нативное подтверждение выполняет пользователь; сервер теста остаётся доступным до ответа, ожидание ограничено 600 секундами. Тайм-аут не означает завершения кода 1С: перед повтором проверить журнал Toolkit и завершение запроса. Успех требует `ORDER_DELIVERY_CONTRACT_GREEN` и одиннадцати наблюдаемых GET: для каждой из трёх локальных причин (`link_save_failed`, `link_conflict`, `ack_pending`) сначала HTTP 503, затем корректные ответы операции и доставки. Причина ошибки должна сохраняться в обеих ветках. Затем явное чтение подтверждённой связи получает поздний `duplicate_task_tag`: ошибка появляется, номер и адрес сохраняются. Исходный Red этой ветки — `ORDER_DELIVERY_RED: подтверждённая связь не показывает поздний конфликт`. HTTP-сервер подставлен; проверка не подтверждает работу реального сервиса Б24. Локальный отчёт исключён из Git.

600 секунд — предел Python-клиента. В исходниках встроенного транспорта Toolkit собственный `RequestTimeout` по умолчанию равен 180 секундам; ответ HTTP 504 может прийти раньше. Подтверждать запрос в течение первой минуты после его появления. После остановки теста ожидающий запрос отклонить вручную; до проверки его завершения новый прогон не запускать. Настройки и код Toolkit этим сценарием не меняются.

## Ссылка заказа при первой записи операции и результата

`queue_order_reference_contract.bsl` вызывает настоящий `ПоставитьВОчередь` для конкретного проведённого демозаказа без операции и перечитывает запись по исходной ссылке. Документ не записывается и не проводится; обмен HTTP не вызывается. Все записи собственных регистров откатываются. До исправления получен `QUEUE_REFERENCE_RED: новая операция не записана под исходным заказом`: `Прочитать()` отсутствующей строки обнулял измерение менеджера. Успех — `QUEUE_REFERENCE_CONTRACT_GREEN`.

`returned_link_reference_contract.bsl` проверяет публичный `Опрос` установленного расширения против временного HTTP-сервера. Синтетическая операция получает результат создания, после чего перечитываются связь, адрес и локальное подтверждение; сервер проверяет точное содержимое ACK. Документы и Б24 не вызываются, настройки и синтетические записи откатываются. До исправления отсутствующей ссылки в первой связи получено исключение «В данной транзакции уже происходили ошибки!» из вложенного обработчика записи ошибки. Обмен должен быть включён. Порт MCP по умолчанию 6004, ожидание ответа до 600 секунд; ручное подтверждение требует тех же ограничений времени, что и проверка доставки выше. При неизвестном ответе проверить завершение кода до повтора. Эти контракты проверяют запись 1С, а не реальную задачу Б24 и срок сквозной доставки.

## Проверка сотрудника без MCP

`rest_settings_right_names_contract.bsl` выполняется на сервере административного MCP: читает список проверяемых прав из исходника REST-модуля и вызывает `ПравоДоступа` для установленного регистра. Первоначальный список воспроизвёл Red «Право Добавление неприменимо»; исправленный список дал `REST_SETTINGS_RIGHT_NAMES_CONTRACT_GREEN`. Тест не читает данные регистра и не заменяет реальный прогон обычного сотрудника после загрузки исправления.

В файловой «КА Демо» после ручной загрузки исходников и обновления расширения открыть новый сеанс `Продажи (ГладилинаВМ)`. Дополнительные роли не нужны. Открыть форму нового заказа, не записывать и не проводить его. В диагностическом блоке нажать «Проверить доступ сотрудника Б24 (демо)».

Ожидаемый результат: `REST_EMPLOYEE_CONTRACT_GREEN; session=...`. Сервер проверяет отсутствие административных прав и привилегированного режима, право изменения заказа, запрет прав на собственный регистр настроек, фактический отказ чтения секрета и записи синтетической настройки. Пробная запись всегда откатывается. Затем установленный REST-модуль читает только существующую демозадачу 10028, проверяет ID и восстановление непривилегированного режима. В журнал регистрации пишется событие `REST_EMPLOYEE_CONTRACT` с тем же номером сеанса; пользователь/сеанс журнала должны соответствовать Гладилиной. Секрет и ответ Б24 в журнал и клиент не передаются. Заказы и задачи не изменяются.

При отказе новая версия возвращает `REST_EMPLOYEE_FAILED; этап: ...; причина: ...`. Причина берётся только из белого списка статических диагностических сообщений; неизвестное исключение обозначается общим внутренним сбоем на указанном этапе. Передать этот безопасный текст для разбора. Предыдущее общее сообщение не позволяет установить причину и не считается успешной проверкой.

Административный сеанс обязан отклоняться: `rest_employee_admin_rejection.bsl` проверяет конкретный отказ. `rest_employee_contract.bsl` выполняет ту же проверку из серверного MCP, если он доступен обычному сотруднику; выдавать роль открытия внешних обработок для этого не требуется. Команда ограничена демобазой, использует фиксированный ID тестовой задачи и не является пользовательским механизмом создания. При диагностическом чтении форма ожидает ответ HTTPS до 20 секунд; фоновый пользовательский поток этим не реализуется.

Сохраняется отдельный собственный тестовый заказ с уникальным комментарием `STAGE3_NATIVE_NEW_`; после успешного проведения операция/задача должны отсутствовать. Исходный заказ не записывается. Перед прогоном сверяется fingerprint; прогресс и ответы — в `.local/stage-3/new-order-posting/`.

После успеха runner закрывает только собственную тестовую форму по точному UUID. При несохранённых правках закрытие отклоняется; ошибки подготовки/проведения оставляют форму для диагностики. Документ не удаляется. Это исключает путаницу с исходной формой в последующих ручных проверках.

При сбое не запускать новую команду вслепую. `--resume-marker <UUID-маркера>` восстанавливает только чтение существующего прогона и не вызывает создание. Если штатное проведение отклонено или остановлено вопросом, сначала установить причину в той же форме. Не считать этот сценарий подтверждением REST из незаписанной формы: он проверяет штатное проведение и сохранение результата при выключенной интеграции.

`--create-task` явно включает REST для одной собственной новой копии и выключает в `finally`; после выполнения обязательно сверяется фактический выключенный допуск. Перед включением неизвестные незавершённые тесты отклоняются. Единственное документированное исключение — старая операция `a75ba748-104a-4735-951d-8554c96e2b9b` в состоянии «Неизвестно» после обрезания маркера задачи10046: она остаётся заблокированной и не отправляется повторно. При неизвестном ответе Toolkit проверять незавершённые запросы подтверждения; не разрешать просроченное включение после выключения.

`run_stage3_ordinary_commands.py --order <UUID>` проверяет обычные штатные помощники записи/проведения на собственной проведённой копии без связи при выключенном REST. Сохраняет только тестовый комментарий, сравнивает состояние интеграции и закрывает свои чистые формы; физические нажатия кнопок не заявлены. `run_stage3_unknown_form.py` только читает документированную старую неизвестную операцию и её нативную форму при повторном открытии.

`run_stage3_manual_result.py` и `stage3_manual_result_contract.bsl` предназначены для проверки результата пользовательского удаления/привязки10058 против локальной исходной точки. **На текущей исходной точке runner не проходит:** версия документа `null`, проверка останавливается до BSL. Сначала установить причину и получить надёжную версию/снимок; не считать прежние сравнения двух пустых версий доказательством отсутствия записи. Результат полного ручного теста ещё требует проверки аудита/истории и неизменности заказа/задачи.

`stage3_posting_error_form_contract.bsl` — начало воспроизводимого сценария отказа предоплаты. Перед выполнением в клиентском контексте проверить fingerprint демобазы и выключенный допуск REST, заменить `__SOURCE_UUID__` на UUID проведённого демозаказа с предоплатой. Сценарий открывает новую неоплаченную копию, заполняет дату отгрузки только в копии и вызывает настоящую команду создания. Исходный заказ не записывается. Ответ `STAGE3_POSTING_ERROR_COMMAND_RETURNED` означает только возврат вызова, **не Green**: штатная запись может продолжаться через отложенную обработку. Форму оставляют открытой для проверки сообщений и технических окон, затем отдельно читают её ссылку, проведение, правки и состояние связи, а также журнал текущего сеанса с момента начала попытки. Ожидается штатный отказ предоплаты, отсутствие записи/проведения/связи и сохранность правок. Сам факт исключения в журнале не доказывает повторное окно; повторения без нового нажатия и видимые окна фиксируются отдельно. После проверки закрывать только эту собственную копию без записи.

`order_data_fingerprint.bsl` — способ контроля данных вместо сравнения двух пустых `ВерсияДанных`; живое чтение и сравнение до/после ручных действий проверены 10 октября 2026 года на собственной копии заказа в КА Демо на Mac. После проверки демобазы подставить UUID собственного тестового заказа и выполнить в серверном контексте до и после ручного действия. Сценарий читает стандартные и обычные реквизиты и все строки табличных частей, возвращая только SHA-256 и признак проведения. Равенство хешей подтверждает равенство данных, но само по себе не исключает перезапись тех же данных или перепроведение; дополнительно проверять события записи документа по точной ссылке с момента исходного снимка и аудит связи. Историческую контрольную точку с пустой версией задним числом не восстанавливает.

`stage3_recreate_cancel_prepare.bsl` подготавливает отдельную форму собственного связанного заказа с несохранённым комментарием. После проверки fingerprint подставить UUID, выполнить в клиентском контексте; физически удалить связь через «Ещё», нажать создание и ответить «Нет» на вопрос с ID прежней связи. До подготовки сохранить исходный хеш данных/проведение, состояние связи и время; после отмены проверить их независимо на сервере, журнал по точной ссылке, отсутствие новой операции и сохранность комментария/модифицированности в тестовой форме. Подготовка сама не вызывает создание, запись или проведение.

`run_stage3_recreate.py --order <UUID> --deleted-task <ID> --preflight-only` проверяет текущую собственную форму после этого сценария, без включения REST. Перед полным прогоном пользователь меняет количество товара штатным интерфейсом так, чтобы передаваемая сумма формы отличалась от записанного заказа. Без `--preflight-only` runner включает допуск, один раз вызывает настоящую команду создания и ждёт физического ответа «Да» на подтверждение с прежним ID. Свежие запросы Toolkit на `stage2Enabled=true` и затем `false` подтверждаются технически; выключение выполняется в `finally` и перечитывается. Ответы/прогресс сохраняются в игнорируемой `.local/stage-3/recreate-attempts/`. Неизвестный результат или тайм-аут запрещают повтор команды до чтения состояния; поля новой задачи, единственность маркера и сохранность прежней задачи проверяются отдельно настоящим REST-чтением. Полный прогон готовится только для разрешённых демозадач.

Предварительное сравнение использует `Товары.Итог("Сумма")`: в этой форме реквизит `СуммаДокумента` может оставаться прежним до штатной записи, несмотря на пересчёт строк. Фактическую переданную сумму после проведения проверять по записанному заказу и снимку новой операции, затем по реальной задаче Б24. `--retry-not-sent` разрешает подготовку только из состояния «НеОтправлена» с подтверждённым `ОтправкаНачата=false`; старый терминальный результат не завершает ожидание нового клика. Резерв, неизвестность и начавшаяся отправка этим режимом не повторяются. Живой повтор после неотправки проверен10октября на Mac: задача10068, актуальная сумма79925KZT, срок от новой операции, REST выключен после проверки. Предшествовавшие сбои фонового выполнения и ограничения описаны в `docs/stage-1-prototypes.md`.

`run_stage3_native_create.py --order <UUID> --close-form` использует `stage3_close_during_create.bsl` только для отдельного собственного заказа с маркером `STAGE3_NATIVE_CLOSE_`, без связи и предыдущей операции. Сценарий один раз вызывает настоящую кнопку; исходную форму закрывает только при сохранённой незавершённой операции и отсутствии несохранённых изменений, затем открывает чистую другую форму. Уже завершённая операция или возврат до штатного проведения не дают Green закрытия. Runner сохраняет состояние при закрытии и требует связь именно той же операции, после чего выключает REST в `finally` и перечитывает допуск. Проверять поля/единственность задачи настоящим REST-чтением и поведение уведомления в другой форме отдельно. Не повторять при неизвестном результате. Проверено10октября: первый прогон остановлен обязательным полем «Дата отгрузки», без операции; после заполнения поля в той же форме получено закрытие при «Резерв», задача10070 и доставка уведомления без возврата в исходный заказ.

`stage3_posting_callback_cancel_contract.bsl` выполняется через `run_stage3_contract.py … --context client` после проверки выключенного REST и сохранения количества записей журнала операций.
