# Этапы работ и задачи: связь заказа клиента 1С:КА с задачей Б24

**Актуальная редакция — 9 октября 2026 года.** Источник требований: [PRD.md](PRD.md), особенно §§3–5 и 9–12. Создание согласовано через входящий вебхук по кнопке в 1С после успешного проведения заказа. «Провести и закрыть» только напоминает; оба ответа продолжают штатное действие. Реализация частичная; результаты проверок приведены ниже, сквозная приёмка остаётся открытой.

План содержит только актуальные задачи T46–T67. Новый вебхук, роли и права проверяются в T46/T47. Прежние проверки регистра и форм не заменяют приёмку новой функции; датированные результаты остаются в [протоколе подготовки](docs/stage-0-readiness.md) и [протоколе прототипов](docs/stage-1-prototypes.md).

По уточнению заказчика создать расширение для базы 1С:КА, используя [Открытие_b24.epf](Открытие_b24.epf) как исходный прототип для переработки. Этот файл — внешняя обработка `.epf`, а итоговый продукт — расширение `.cfe`. Пригодные части логики переносить из имеющихся [BSL/XML-исходников](src/Открытие_b24/), учитывая [существующий прототип расширения](src/stage-1-prototype/README.md). Старый браузерный сценарий заменить согласованным REST-созданием по кнопке; пригодность конкретных частей ещё требует проверки.

Python-служба исключена 7 октября и удалена с зависимыми тестами; [аудит](docs/stage-1-cleanup.md). Новая схема не требует восстановления service/SQLite/entity/worker. Прямой HTTPS из расширения — кандидат проверки, не готовая архитектура.

## Правила выполнения актуального плана

- Работать с «Заказом клиента» в существующей «КА Демо» и задачами существующего проекта «Гем платежи демо». Не добавлять участников в проект и не менять рабочие объекты.
- Сторона 1С — расширение без изменения основной конфигурации. Поставка — проверенный `.cfe`, исходники, инструкции и фактические результаты. EPF, MCP и Python не требуются пользователю.
- Создание — REST по явной кнопке; после создания только сообщение в 1С. В форме и списке отображается ID задачи обычным текстом; открытия из 1С нет, сотрудник переходит в Б24 самостоятельно (решение 9 октября).
- Для нового поведения/дефектов применять Red → Green → Refactor небольшими шагами. Для поведения только в приложениях фиксировать исходный сбой и повторный успешный прогон; отсутствие автоматизации указывать отдельно. Статические проверки и моки не заменяют живую приёмку.
- Перед правками проверять Git, читать затронутые файлы и сохранять чужие изменения. Секрет вебхука не включать в исходники, логи, `.cfe` и документы. Предоставленные scopes не считать доказательством фактических прав.
- Результаты вести в `docs/stage-1-prototypes.md`: дата, среда, шаги, ожидаемый/фактический результат, подтверждение, ограничения. `[x]` ставить только после выполнения критерия и его проверки.

После отката резервной копии создание включается программистом только после ручной сверки. Работа одного сотрудника в двух сеансах и группировка уведомлений исключены из приёмки. Отметки выполнения ставятся только после соответствующего живого критерия. Исключение для этапа 2: заказчик 9 октября 2026 года закрыл этап с отказом от оставшихся проверок; отметки T67/T49/T50/T56 означают это решение, а не успешное прохождение непроведённых сценариев.

- [x] **T49. Подготовить устойчивую операцию и атомарную защиту.** Адаптировать имеющиеся регистры: база, заказ, операция, инициатор, состояние, снимок отправляемых данных/срока, ID задачи и подтверждение связи; отдельно хранить подтверждённую неотправку и созданную задачу с несохранённой связью. До отправки атомарно резервировать попытку; сохранить уникальность связи один к одному и первую связь при конфликте. Инициатор первой операции сохраняется при повторе и конкурентном нажатии. Готово: повторы/конкуренция проверены, незавершённые старые заявки не переносятся в новый поток автоматически; сохранение связи не проводит заказ повторно.

Не смешивать неизвестный результат с достоверно подтверждённой неотправкой: последняя не отправляется автоматически после восстановления сети или запуска клиента. Готово: исходный сбой воспроизведён, повторная проверка восстанавливает ту же задачу без новой отправки создания; неизвестность блокирует создание только для данного заказа. Данные и срок попытки после полуночи не пересчитываются. При длительной недоступности сохраняется «Проверяем, создана ли задача» до подтверждения результата; время ожидания не разрешает новую отправку.

Однократно сравнить сохранённые передаваемые данные заказа со снимком попытки: при расхождении дополнительно показать неблокирующее предупреждение по PRD §5, без изменения задачи и постоянного наблюдения. Добавить неблокирующее напоминание по PRD §4 после успешной отмены заказа или установки пометки на удаление при существующей связи; задачу и связь сохранять. Готово: уведомление успеха только после записи и с данными исходного заказа; предупреждение только при расхождении передаваемых данных; при доступных системах оба срока ≤60 секунд соблюдены, включая следующий запуск клиента; проведение не отменяется, секрет не попадает в диагностику.
