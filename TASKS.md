# Этапы работ и задачи: связь заказа клиента 1С:КА с задачей Б24

**Актуальная редакция — 8 октября 2026 года.** Источник требований: [PRD.md](PRD.md), особенно §§3–5 и 9–12. Создание согласовано через входящий вебхук по кнопке в 1С после успешного проведения заказа. «Провести и закрыть» только напоминает; оба ответа продолжают штатное действие. Новый REST-сценарий ещё не реализован и не проверен.

План содержит только актуальные задачи T46–T67. Новый вебхук, роли и права проверяются в T46/T47. Прежние проверки регистра и форм не заменяют приёмку новой функции; датированные результаты остаются в [протоколе подготовки](docs/stage-0-readiness.md) и [протоколе прототипов](docs/stage-1-prototypes.md).

По уточнению заказчика создать расширение для базы 1С:КА, используя [Открытие_b24.epf](Открытие_b24.epf) как исходный прототип для переработки. Этот файл — внешняя обработка `.epf`, а итоговый продукт — расширение `.cfe`. Пригодные части логики переносить из имеющихся [BSL/XML-исходников](src/Открытие_b24/), учитывая [существующий прототип расширения](src/stage-1-prototype/README.md). Старый браузерный сценарий заменить согласованным REST-созданием по кнопке; пригодность конкретных частей ещё требует проверки.

Python-служба исключена 7 октября и удалена с зависимыми тестами; [аудит](docs/stage-1-cleanup.md). Новая схема не требует восстановления service/SQLite/entity/worker. Прямой HTTPS из расширения — кандидат проверки, не готовая архитектура.

## Правила выполнения актуального плана

- Работать с «Заказом клиента» в существующей «КА Демо» и задачами существующего проекта «Гем платежи демо». Не добавлять участников в проект и не менять рабочие объекты.
- Сторона 1С — расширение без изменения основной конфигурации. Поставка — проверенный `.cfe`, исходники, инструкции и фактические результаты. EPF, MCP и Python не требуются пользователю.
- Создание — REST по явной кнопке; после создания только сообщение в 1С. Открытие существующей задачи — отдельное действие в десктопном Б24. Браузер не является пользовательским переходом.
- Для нового поведения/дефектов применять Red → Green → Refactor небольшими шагами. Для поведения только в приложениях фиксировать исходный сбой и повторный успешный прогон; отсутствие автоматизации указывать отдельно. Статические проверки и моки не заменяют живую приёмку.
- Перед правками проверять Git, читать затронутые файлы и сохранять чужие изменения. Секрет вебхука не включать в исходники, логи, `.cfe` и документы. Предоставленные scopes не считать доказательством фактических прав.
- Результаты вести в `docs/stage-1-prototypes.md`: дата, среда, шаги, ожидаемый/фактический результат, подтверждение, ограничения. `[x]` ставить только после выполнения критерия и его проверки.

## Этап 1. REST и настройки

Основание: PRD §§2, 5, 8, 10.

- [ ] **T46. Проверить предоставленный вебхук и новые ID.** Выполнить чтение фактических прав владельца, scopes и аккаунтов Оксаны, Людмилы, Евгения, Кирилла; подтвердить существующий демопроект (исторический кандидат ID `36`). Готово: ID проверены, не выбраны только по именам или `user/30`; `user_basic`, `task`, `sonet_group` и ограничения подтверждены без вывода секрета. Новые права/участники в проект автоматически не добавляются.
- [ ] **T47. Проверить реальное REST-создание с точными ролями.** На тестовом объекте демопроекта создать и перечитать задачу: Оксана постановщик, Людмила исполнитель, Евгений и Кирилл наблюдатели, соисполнителей нет, название `{Контрагент}.`, крайний срок — текущий день, 19:00 UTC+5. Готово: сохранённые поля и права подтверждены API; нехватка прав зафиксирована, подмена постановщика отсутствует. Прогон с владельцем вебхука не заменяет проверку прав обычного сотрудника 1С.
- [ ] **T48. Проверить и реализовать безопасные настройки обмена.** Проверить прямой HTTPS из расширения на демоплатформе, выбрать место исполнения и хранение секрета вне исходников/поставки, настроить проверенные ID и портал. Готово: обычный сотрудник не читает секрет; неверные настройки дают понятную ошибку; Python-служба не требуется. Дополнительные компоненты сначала согласовать, если прямой вариант недостаточен.

## Этап 2. Основа расширения, операции, связь и восстановление

Основание: PRD §§4, 7, 8, 10. Живые проверки зависят от T46–T48.

- [ ] **T67. Создать основу расширения для 1С:КА с переработкой имеющегося прототипа.** Разобрать `Открытие_b24.epf` и его BSL/XML-исходники, определить пригодные части и адаптировать их к расширению с учётом `src/stage-1-prototype/`. Реализовать согласованный сценарий в расширении без изменения основной конфигурации и запуска внешней обработки пользователем. Готово: исходники расширения сохранены, состав объектов и перенесённой логики описан, основа `.cfe` проходит штатные проверки и применяется в «КА Демо». Браузерный переход и требование держать EPF открытой в итоговый сценарий не переносятся; функции и их приёмка выполняются в T49–T62.
- [ ] **T49. Подготовить устойчивую операцию и атомарную защиту.** Адаптировать имеющиеся регистры: база, заказ, операция, инициатор, состояние, снимок отправляемых данных/срока, ID задачи и подтверждение связи. До отправки атомарно резервировать попытку; сохранить уникальность связи один к одному и первую связь при конфликте. Готово: повторы/конкуренция проверены, незавершённые старые заявки не переносятся в новый поток автоматически; сохранение связи не проводит заказ повторно.
- [ ] **T50. Проверить восстановление неизвестного REST-результата.** Выбрать достоверную корреляцию операции с задачей после потери ответа; не искать по названию/сумме. Готово: исходный сбой воспроизведён, повторная проверка восстанавливает ту же задачу без новой отправки создания; неизвестность блокирует создание только для данного заказа. Данные и срок попытки после полуночи не пересчитываются.
- [ ] **T56. Реализовать возврат, восстановление и сообщения.** Сохранить подтверждённые ID, ссылку и название, обновить форму, различать отказ API, неизвестный результат и ошибку записи связи. Готово: сообщение успеха после записи; при доступных системах оба срока ≤60 секунд соблюдены, включая следующий запуск клиента; проведение не отменяется, секрет не попадает в диагностику.

## Этап 3. Команды и интерфейс

Основание: PRD §§3–5, 7. Основа расширения — T67; REST-включение зависит от T47–T50.

- [ ] **T51. Реализовать кнопку «Создать задачу в Битрикс24».** Разместить под верхними командами. При существующей связи сообщить о задаче без создания; при неизвестной попытке перейти к восстановлению. Иначе сначала штатно провести заказ, затем создать по API по сохранённым данным. Готово: новый/изменённый/проведённый заказ проверены; отказ/отмена исключают REST; после успеха сообщение в 1С без открытия Б24 и без предварительной формы. Название пока `{Контрагент}.`; описание по PRD §5; крайний срок — текущий день, 19:00 UTC+5.
- [ ] **T52. Заменить автоматическое открытие напоминанием.** При каждом «Провести и закрыть» вопрос «Вы создали задачу в Битрикс24?», оба ответа продолжают штатные проверки/проведение/закрытие. Готово: связь не влияет на показ вопроса; «Да» не устанавливает признак и не привязывает задачу; «Нет» не блокирует работу; обычные запись/проведение не показывают вопрос; прежняя очередь/автоматическое открытие отключены от этого действия.
- [ ] **T53. Убрать нижний блок и добавить верхние сведения.** Рядом с командой создания вывести только для чтения «Задача создана», ID и название из сохранённой связи, а также отдельное состояние неизвестной попытки. Готово: прежнего нижнего диагностического блока нет; отсутствие связи, восстановление, подтверждённое создание и ручная привязка показаны корректно; ответ на напоминание сведения не меняет.
- [ ] **T54. Сохранить колонку списка и отдельное открытие задачи.** Колонка «Задача Б24» после «Клиент», `Задача №{ID}`; верхняя команда «Открыть задачу» и ячейка используют одну связь. Готово: актуальные данные после обновления, нужная задача открывается только в десктопном Б24 у инициатора; ошибка открытия сохраняет связь и не открывает браузер. REST-создание не зависит от установленного десктопного клиента.
- [ ] **T55. Сохранить ручное управление связью через «Ещё».** Привязка существующей задачи, изменение и удаление: портал/ID/название, отдельная проверка доступности, атомарная уникальность, право изменения, подтверждение и аудит. Готово: неверная/занятая ссылка отклоняется; отмена сохраняет связь; данные и сама задача Б24 не изменяются и не удаляются; проведение и создание не запускаются.

## Этап 4. Сквозная приёмка

Основание: PRD §9 целиком. Зависимость: T46–T56, T67. В каждой задаче записать фактический результат всех относящихся к ней строк PRD §9; непроверенные строки остаются открытыми.

- [ ] **T57. Проверить проведение и напоминание.** Новый/изменённый/проведённый заказ, отказ и отмена проведения, оба ответа при пустой и существующей связи, повторные действия и отказ после ответа. Готово: порядок «проведение → REST» соблюдён; обычные команды, напоминание и закрытие формы не создают задачу и не обходят штатные проверки.
- [ ] **T58. Проверить данные и реальные права.** Перечитать созданные задачи: название, описание, крайний срок (текущий день, 19:00 UTC+5), Оксана, Людмила, два наблюдателя, отсутствие соисполнителей и демопроект. Проверить другого сотрудника 1С, доступ к заказу/секрету и ошибки прав вебхука. Готово: подмена ролей отсутствует, последующие ручные изменения Б24 не перезаписываются интеграцией.
- [ ] **T59. Проверить повторы, конфликты и потерю ответа.** Повтор кнопки, конкурентные сеансы, неизвестный результат, созданная задача до записи связи, повтор результата, закрытие клиента и восстановление после полуночи. Готово: дублей и молчаливой замены нет; одна связь; оба срока ≤60 секунд измерены, заказ не перепроводится восстановлением.
- [ ] **T60. Проверить форму, список и ручную связь.** Верхние сведения, отсутствие нижнего блока, обновление, колонка, все команды «Ещё», неверная/занятая ссылка, отмена, аудит и недоступная задача. Проверить отдельное десктопное открытие, включая закрытое/отсутствующее приложение и отсутствие авторизации. Готово: браузер не открывается; создание по REST при закрытом десктопном Б24 проверено отдельно.
- [ ] **T61. Проверить новый сеанс и независимость поставки.** Применить CFE и проверить функции без внешних EPF, MCP, Python-службы и прежнего worker/entity-потока. Зафиксировать платформу, конфигурацию, совместимость, клиент, ОС и десктопный Б24; другой ПК и права сотрудника не выводить из проверки текущего ПК. Готово: основная конфигурация не изменена, ограничения среды перечислены.
- [ ] **T62. Устранить дефекты и закрыть матрицу PRD §9.** Для дефектов зафиксировать Red и Green, повторить затронутые проверки после рефакторинга. Готово: все обязательные строки имеют успешный фактический результат; непроверенные права/среды не выданы за пройденную приёмку; новый сценарий не закрыт историческими отметками.

## Этап 5. Передача программисту и внедрение

- [ ] **T63. Готово: бинарник соответствует проверенным исходникам нового сценария, секреты и рабочие данные отсутствуют.

После успешной проверки установить расширение без замены основной конфигурации, `.cf` и сравнения/объединения. Готово: версия, настройки, результат и ограничения внедрения зафиксированы.
