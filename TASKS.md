# Этапы работ и задачи: связь заказа клиента 1С:КА с задачей Б24

**Актуальная редакция — 8 октября 2026 года.** Источник требований: [PRD.md](PRD.md), особенно §§3–5 и 9–12. Создание согласовано через входящий вебхук по кнопке в 1С после успешного проведения заказа. «Провести и закрыть» только напоминает; оба ответа продолжают штатное действие. Новый REST-сценарий ещё не реализован и не проверен.

План содержит только актуальные задачи T46–T67. Новый вебхук, роли и права проверяются в T46/T47. Прежние проверки регистра и форм не заменяют приёмку новой функции; датированные результаты остаются в [протоколе подготовки](docs/stage-0-readiness.md) и [протоколе прототипов](docs/stage-1-prototypes.md).

По уточнению заказчика создать расширение для базы 1С:КА, используя [Открытие_b24.epf](Открытие_b24.epf) как исходный прототип для переработки. Этот файл — внешняя обработка `.epf`, а итоговый продукт — расширение `.cfe`. Пригодные части логики переносить из имеющихся [BSL/XML-исходников](src/Открытие_b24/), учитывая [существующий прототип расширения](src/stage-1-prototype/README.md). Старый браузерный сценарий заменить согласованным REST-созданием по кнопке; пригодность конкретных частей ещё требует проверки.

Python-служба исключена 7 октября и удалена с зависимыми тестами; [аудит](docs/stage-1-cleanup.md). Новая схема не требует восстановления service/SQLite/entity/worker. Прямой HTTPS из расширения — кандидат проверки, не готовая архитектура.

## Правила выполнения актуального плана

- Работать с «Заказом клиента» в существующей «КА Демо» и задачами существующего проекта «Гем платежи демо». Не добавлять участников в проект и не менять рабочие объекты.
- Сторона 1С — расширение без изменения основной конфигурации. Поставка — проверенный `.cfe`, исходники, инструкции и фактические результаты. EPF, MCP и Python не требуются пользователю.
- Создание — REST по явной кнопке; после создания только сообщение в 1С. Открытие существующей задачи — отдельное действие в десктопном Б24. Браузер не является пользовательским переходом.
- Для нового поведения/дефектов применять Red → Green → Refactor небольшими шагами. Для поведения только в приложениях фиксировать исходный сбой и повторный успешный прогон; отсутствие автоматизации указывать отдельно. Статические проверки и моки не заменяют живую приёмку.
- Перед правками проверять Git, читать затронутые файлы и сохранять чужие изменения. Секрет вебхука не включать в исходники, логи, `.cfe` и документы. Предоставленные scopes не считать доказательством фактических прав.
- Результаты вести в `docs/stage-1-prototypes.md`: дата, среда, шаги, ожидаемый/фактический результат, подтверждение, ограничения. `[x]` ставить только после выполнения критерия и его проверки.

## Этап 1. REST и настройки

Основание: PRD §§2, 5, 8, 10.

- [ ] **T46. Проверить предоставленный вебхук и новые ID.** Выполнить чтение фактических прав владельца, scopes и аккаунтов Оксаны, Людмилы, Евгения, Кирилла; подтвердить существующий демопроект (исторический кандидат ID `36`). Готово: ID проверены, не выбраны только по именам или `user/30`; `user_basic`, `task`, `sonet_group` и ограничения подтверждены без вывода секрета. Новые права/участники в проект автоматически не добавляются.
- [ ] **T47. Проверить реальное REST-создание с точными ролями.** На тестовом объекте демопроекта создать и перечитать задачу: Оксана постановщик, Людмила исполнитель, Евгений и Кирилл наблюдатели, соисполнителей нет, название `{Контрагент} — заказ №{НомерЗаказа} от {ДатаЗаказа}.`, крайний срок — 19:00 UTC+5: при начале новой попытки до 19:00 сегодня, с 19:00 — следующий календарный день, включая выходные и праздники. Готово: сохранённые поля и права подтверждены API; нехватка прав зафиксирована, подмена постановщика отсутствует. Прогон с владельцем вебхука не заменяет проверку прав обычного сотрудника 1С.
- [ ] **T48. Проверить и реализовать безопасные настройки обмена.** Проверить прямой HTTPS из расширения на демоплатформе, выбрать место исполнения и хранение секрета вне исходников/поставки, настроить проверенные ID и портал. Подтвердить возможность фонового REST-вызова на файловой демобазе без блокировки интерфейса и зависимости от открытой формы заказа. Готово: обычный сотрудник не читает секрет; неверные настройки дают понятную ошибку; Python-служба не требуется. Дополнительные компоненты сначала согласовать, если прямой вариант недостаточен.

## Этап 2. Основа расширения, операции, связь и восстановление

Основание: PRD §§4, 7, 8, 10. Живые проверки зависят от T46–T48.

- [ ] **T67. Создать основу расширения для 1С:КА с переработкой имеющегося прототипа.** Разобрать `Открытие_b24.epf` и его BSL/XML-исходники, определить пригодные части и адаптировать их к расширению с учётом `src/stage-1-prototype/`. Реализовать согласованный сценарий в расширении без изменения основной конфигурации и запуска внешней обработки пользователем. Готово: исходники расширения сохранены, состав объектов и перенесённой логики описан, основа `.cfe` проходит штатные проверки и применяется в «КА Демо». Браузерный переход и требование держать EPF открытой в итоговый сценарий не переносятся; функции и их приёмка выполняются в T49–T62.
- [ ] **T49. Подготовить устойчивую операцию и атомарную защиту.** Адаптировать имеющиеся регистры: база, заказ, операция, инициатор, состояние, снимок отправляемых данных/срока, ID задачи и подтверждение связи; отдельно хранить подтверждённую неотправку и созданную задачу с несохранённой связью. До отправки атомарно резервировать попытку; сохранить уникальность связи один к одному и первую связь при конфликте. Инициатор первой операции сохраняется при повторе и конкурентном нажатии. Готово: повторы/конкуренция проверены, незавершённые старые заявки не переносятся в новый поток автоматически; сохранение связи не проводит заказ повторно.
- [ ] **T50. Проверить восстановление неизвестного REST-результата.** Выбрать достоверную корреляцию операции с задачей после потери ответа; не искать по названию/сумме. Не смешивать неизвестный результат с достоверно подтверждённой неотправкой: последняя не отправляется автоматически после восстановления сети или запуска клиента. Готово: исходный сбой воспроизведён, повторная проверка восстанавливает ту же задачу без новой отправки создания; неизвестность блокирует создание только для данного заказа. Данные и срок попытки после полуночи не пересчитываются. При длительной недоступности сохраняется «Проверяем, создана ли задача» до подтверждения результата; время ожидания не разрешает новую отправку.
- [ ] **T56. Реализовать возврат, восстановление и сообщения.** Сохранить подтверждённые ID, ссылку и название, обновить открытую форму исходного заказа, различать подтверждённую неотправку, отказ API, неизвестный результат и ошибку записи связи. При известном ID до записи связи сразу показать «Задача №{ID} создана. Связь с заказом ещё не сохранена» и автоматически восстановить ту же связь; при подтверждённой неотправке — «Задача не создана. Повторите позже», без автоматической очереди. После записи связи показать сотруднику-инициатору первой попытки неблокирующее уведомление «По заказу №{НомерЗаказа} от {ДатаЗаказа} создана задача №{ID}», в том числе при закрытой форме или другом активном заказе, без ответа «ОК», открытия окон и переключения фокуса. Однократно сравнить сохранённые передаваемые данные заказа со снимком попытки: при расхождении дополнительно показать неблокирующее предупреждение по PRD §5, без изменения задачи и постоянного наблюдения. Добавить неблокирующее напоминание по PRD §4 после успешной отмены заказа или установки пометки на удаление при существующей связи; задачу и связь сохранять. Готово: уведомление успеха только после записи и с данными исходного заказа; предупреждение только при расхождении передаваемых данных; при доступных системах оба срока ≤60 секунд соблюдены, включая следующий запуск клиента; проведение не отменяется, секрет не попадает в диагностику.

## Этап 3. Команды и интерфейс

Основание: PRD §§3–5, 7. Основа расширения — T67; REST-включение зависит от T47–T50.

- [ ] **T51. Реализовать кнопку «Создать задачу в Битрикс24».** Разместить под верхними командами. При существующей связи сообщить о задаче без создания; при выполняющейся попытке сообщить «Задача уже создаётся» без новой попытки и запроса; при неизвестной попытке перейти к восстановлению. Если связь ранее явно удалили, до проведения получить подтверждение с ID последней удалённой связи по PRD §3.1; при отмене не проводить этой командой и не создавать. После подтверждения повторно атомарно проверить связь и попытку. Иначе сначала штатно провести заказ, сохранить устойчивую операцию и создать по API в фоне по сохранённым данным. После запуска сотрудник может продолжить работу, открыть другой заказ или закрыть форму; до результата блокируется только повторное создание для того же заказа. Готово: новый/изменённый/проведённый заказ проверены; отказ/отмена исключают REST; после успеха сообщение в 1С без открытия Б24 и без предварительной формы; перед первым созданием дополнительного вопроса о ранее созданной вручную задаче нет; после подтверждённой неотправки требуется новый клик с актуальными проведёнными данными и заново рассчитанным сроком. Название `{Контрагент} — заказ №{НомерЗаказа} от {ДатаЗаказа}.`; описание по PRD §5; крайний срок — 19:00 UTC+5: при начале новой попытки до 19:00 сегодня, с 19:00 — следующий календарный день, включая выходные и праздники; срок сохраняется в операции без пересчёта при восстановлении.
- [ ] **T52. Заменить автоматическое открытие напоминанием.** При каждом «Провести и закрыть» вопрос «Вы создали задачу в Битрикс24?», оба ответа продолжают штатные проверки/проведение/закрытие. Готово: связь не влияет на показ вопроса; «Да» не устанавливает признак и не привязывает задачу; «Нет» не блокирует работу; обычные запись/проведение не показывают вопрос; прежняя очередь/автоматическое открытие отключены от этого действия.
- [ ] **T53. Убрать нижний блок и добавить верхние сведения.** Рядом с командой создания вывести только для чтения «Задача создана», ID и название из сохранённой связи, а также состояния «Создаём задачу» и «Проверяем, создана ли задача» из сохранённой операции, включая повторное открытие формы. При подтверждённом ID до записи связи показать «Задача №{ID} создана. Связь с заказом ещё не сохранена» отдельно от полей/признака сохранённой связи; название после переименования в Б24 не обновлять. При длительной недоступности состояние проверки сохраняется до подтверждения результата, без отдельного сообщения/команды по таймеру. Готово: прежнего нижнего диагностического блока нет; отсутствие связи, создание в фоне, восстановление, подтверждённое создание и ручная привязка показаны корректно; ответ на напоминание сведения не меняет.
- [ ] **T54. Сохранить колонку списка и отдельное открытие задачи.** Колонка «Задача Б24» после «Клиент», `Задача №{ID}`; верхняя команда «Открыть задачу» и ячейка используют одну связь. Готово: актуальные данные после обновления, нужная задача открывается только в десктопном Б24 у инициатора; ошибка открытия сохраняет связь и не открывает браузер. REST-создание не зависит от установленного десктопного клиента.
- [ ] **T55. Сохранить ручное управление связью через «Ещё».** Привязка существующей задачи, изменение и удаление: портал/ID/название, отдельная проверка доступности, атомарная уникальность, право изменения, подтверждение и аудит. Сохранять ID последней явно удалённой связи для подтверждения нового создания в T51. Готово: неверная/занятая ссылка отклоняется; отмена сохраняет связь; данные и сама задача Б24 не изменяются и не удаляются; проведение и создание не запускаются.

## Этап 4. Сквозная приёмка

Основание: PRD §9 целиком. Зависимость: T46–T56, T67. В каждой задаче записать фактический результат всех относящихся к ней строк PRD §9; непроверенные строки остаются открытыми.

- [ ] **T57. Проверить проведение и напоминание.** Новый/изменённый/проведённый заказ, отказ и отмена проведения, оба ответа при пустой и существующей связи, повторные действия и отказ после ответа. Готово: порядок «проведение → REST» соблюдён; обычные команды, напоминание и закрытие формы не создают задачу и не обходят штатные проверки.
- [ ] **T58. Проверить данные и реальные права.** Перечитать созданные задачи: название по новому формату (номер с сохранением ведущих нулей, дата ДД.ММ.ГГГГ), описание, крайний срок по PRD §5 (до 19:00 — сегодня, с 19:00 — следующий календарный день, 19:00 UTC+5, включая выходные и праздники), Оксана, Людмила, два наблюдателя, отсутствие соисполнителей и демопроект. Проверить границу 18:59:59/19:00:00/19:00:01, переход на выходной, новый месяц и год, ответ после смены даты без пересчёта срока. Проверить изменение и сохранение суммы/контрагента во время создания или восстановления: в задаче первоначальные данные, после записи связи неблокирующее предупреждение; без расхождения или при изменении только непередаваемых реквизитов предупреждения нет. Проверить другого сотрудника 1С, доступ к заказу/секрету и ошибки прав вебхука. Готово: подмена ролей отсутствует, последующие ручные изменения Б24 не перезаписываются интеграцией.
- [ ] **T59. Проверить повторы, конфликты и потерю ответа.** Повтор кнопки, конкурентные сеансы, неизвестный результат, созданная задача до записи связи, повтор результата, работа с другим заказом и закрытие/повторное открытие формы во время фонового создания, закрытие клиента и восстановление после полуночи. Проверить уведомление после записи связи при другом активном заказе или закрытой форме: правильные номер/дата исходного заказа и ID задачи, без модального окна, автоматического открытия и переключения фокуса. Проверить два конкурентных сеанса: одна попытка и один REST-запрос создания; второму сотруднику «Задача уже создаётся», уведомление успеха только первому, второму та же связь доступна после обновления; инициатор первой операции не заменяется. Проверить недоступность более пяти минут: прежняя попытка и состояние «Проверяем, создана ли задача» сохраняются, нового создания и отдельного сообщения/команды по таймеру нет; после восстановления доступности соблюдены прежние сроки восстановления. Проверить известный ID при ошибке записи связи: частичное состояние сразу, тот же ID после автоматического восстановления, полное уведомление только после записи. Проверить подтверждённую неотправку: нет автоматического запроса после восстановления сети/нового запуска; новый клик использует актуальные сохранённые данные и срок; потеря ответа после возможной отправки остаётся неизвестным результатом. Готово: REST-ожидание не блокирует интерфейс; повторное создание для незавершённой попытки блокируется, другие заказы доступны; дублей и молчаливой замены нет; одна связь; оба срока ≤60 секунд измерены, заказ не перепроводится восстановлением.

## Фиксация этой редакции

8 октября изменены только PRD и план: согласованный REST-сценарий, роли, верхние сведения и актуальный перечень задач; прежние этапы удалены из плана по решению заказчика. Добавлена T67: создание расширения КА с использованием `Открытие_b24.epf` как исходного прототипа для переработки. В последовательном разборе эдж кейсов заказчик выбрал перенос срока после 19:00 на следующий календарный день: до 19:00 — сегодня, с 19:00 — завтра, 19:00 UTC+5, включая выходные и праздники; восстановление срок не меняет. T47, T51, T58 и матрица PRD дополнены этим правилом и проверками границы/календарных переходов. Это изменение документации, без Red/Green для поведения. Код расширения, CFE, вебхук и портал этой редакцией не изменялись; живые проверки не выполнялись. Новые задачи T46–T67 остаются открытыми.

В том же разборе подтверждены ручная привязка ранее созданной задачи через «Ещё» без дополнительного вопроса перед созданием и создание в фоне: сотрудник сразу продолжает работу или закрывает форму, состояние попытки сохраняется, повторное создание блокируется только для этого заказа. T48, T51, T53, T59 и PRD дополнены требованиями и приёмкой; механизм фонового выполнения ещё не проверен. Изменены только документы, без изменения кода/поставки и без живого REST-прогона.

Для результата фонового создания заказчик выбрал неблокирующее уведомление в 1С с номером/датой исходного заказа и ID задачи после записи связи: без «ОК», открытия окон и переключения фокуса, включая закрытую форму и другой активный заказ. Дополнительно подтверждено неблокирующее предупреждение, если во время попытки изменили и сохранили передаваемые данные заказа: первоначальный снимок и задача не изменяются, дальнейшее постоянное наблюдение не вводится. Обновлены PRD, T56, T58 и T59; это требования и сценарии приёмки, а не подтверждённая реализация. Код и поставка не изменялись, живые проверки не выполнялись.

Название уточнено заказчиком в том же разборе: `{Контрагент} — заказ №{НомерЗаказа} от {ДатаЗаказа}.`, дата ДД.ММ.ГГГГ, номер с сохранением ведущих нулей.
