# ТЗ: связь заказа клиента в 1С:КА с задачей Битрикс24

Статус: сценарий создания через REST согласован 8 октября 2026 года; реализация частичная, сквозная приёмка не завершена. Проверенные результаты — в `docs/stage-1-prototypes.md`. 10 октября при разборе этапа 4 заказчик изменил название, целевой проект и состав участников; актуальные правила и оставшиеся уточнения — в §5. Прежние прогоны не подтверждают новое заполнение.
Дата редакции: 10 октября 2026 года. Открытие задач из 1С исключено по уточнению заказчика 9 октября; в форме и списке отображается ID, сотрудник переходит в Б24 самостоятельно. Решения этой редакции заменяют прежний сценарий автоматического открытия формы Б24; технические вопросы перечислены в разделе 10.

## 1. Цель и границы продукта

Позволить сотруднику создать задачу Битрикс24 по проведённому заказу клиента кнопкой в 1С, автоматически сохранить связь и напомнить о задаче при «Провести и закрыть». Создание задачи необязательно. Создание заказов из Б24 исключено из объёма; выставление счетов остаётся в КА.

Документ первой версии — **«Заказ клиента»**, путь: **Продажи → Заказы клиентов → Создать**. Заказчик повторно подтвердил этот документ 8 октября. Упоминание «Счёта на оплату» в исходной задаче директора №9866 и формулировка «Счета на Оплату» в новом названии не меняют выбранный тип документа. По уточнению 10 октября номер, дата и сумма для задачи берутся из заказа; отдельный документ счёта для создания задачи не требуется.

Задача создаётся через REST API и входящий вебхук только по явному нажатию «Создать задачу в Битрикс24» в 1С. Перед REST-вызовом выполняется штатное проведение заказа. Предварительная форма редактирования задачи в 1С или Б24 не открывается. «Провести и закрыть», ответы на напоминание и обычные «Записать»/«Провести» сами задачу не создают.

После создания и записи связи показывается неблокирующее уведомление в 1С с номером и датой исходного заказа и ID задачи; текущая работа не прерывается, окна автоматически не открываются и фокус не переключается. Команды открытия и переходы из списка отсутствуют. Сотрудник самостоятельно находит задачу в Б24 по ID из 1С. Наличие запущенного десктопного Б24 не требуется для REST-создания задачи.

## 3. Основные сценарии

### 3.1. Создание задачи кнопкой

1. Сотрудник открывает или создаёт заказ, заполняет его и нажимает «Создать задачу в Битрикс24».
2. Если связь уже существует, новую задачу не создавать и связь не заменять; сообщить об имеющейся задаче. Если результат прежней попытки неизвестен, сначала восстановить эту попытку по разделу 7. Если связь ранее явно удалили, перед проведением и новой попыткой запросить подтверждение «Ранее заказ был связан с задачей №{ID}. Создать новую?» с ID последней удалённой связи из аудита. При отмене не проводить заказ этой командой и не запускать создание; после подтверждения повторно атомарно проверить текущую связь и попытку. При первом создании дополнительного подтверждения нет.
3. Для заказа без связи и незавершённой попытки выполнить штатные проверки и проведение документа, включая новый заказ и несохранённые изменения. Отказ, ошибка или отмена проведения прекращают создание: REST не вызывается.
4. После успешного проведения получить сохранённые данные заказа, зафиксировать устойчивую операцию и отправить запрос создания задачи через настроенный вебхук. Между проверкой состояния и отправкой обеспечить защиту от повторных/конкурирующих попыток.
5. Создать задачу с данными раздела 5. Сотрудник не подтверждает сохранение в отдельной форме Б24.
6. По подтверждённому результату автоматически сохранить ID, ссылку и название задачи в связи исходного заказа. Показать сотруднику-инициатору попытки неблокирующее уведомление «По заказу №{НомерЗаказа} от {ДатаЗаказа} создана задача №{ID}» и обновить сведения в открытой форме исходного заказа; список после обновления использует ту же связь. Уведомление не требует ответа «ОК», не открывает исходную форму или Б24 и не переключает фокус.

Ошибка API или записи связи не отменяет уже успешное проведение. Связь записывается без повторного проведения и изменения данных заказа. Сбой после отправки запроса не разрешает повторное создание без проверки прежней операции.

После успешного проведения и сохранения устойчивой операции создание выполняется в фоне: сотрудник сразу может продолжить работу, открыть другой заказ или закрыть исходную форму, не ожидая REST-ответа. Закрытие формы не отменяет отправленную попытку. До завершения создания или проверки неизвестного результата блокируется только повторное создание для того же заказа. При закрытии клиента 1С состояние попытки сохраняется; проверка и восстановление выполняются при следующем запуске по §7. Требование фонового выполнения согласовано при разборе эдж кейсов 8 октября; механизм на файловой демобазе ещё не проверен.

Если исходная форма уже закрыта или сотрудник работает с другим заказом, результат показывается тем же неблокирующим уведомлением в 1С. Номер, дата и связь относятся к исходному заказу операции, а не к активной форме. Сохранённый ID также доступен при следующем открытии исходного заказа и обновлении списка. Этот способ сообщения выбран заказчиком при разборе эдж кейсов 8 октября; живое поведение ещё не проверено.

Если другой сотрудник одновременно нажимает создание по тому же заказу и попытка уже выполняется, показать ему «Задача уже создаётся», без новой попытки и нового REST-запроса создания. Не подключать его к отдельному ожиданию уведомления об успехе: уведомление получает только сотрудник-инициатор первой попытки. Второй сотрудник может продолжить работу; после завершения и обновления исходного заказа или списка ему доступна та же сохранённая связь. Инициатор существующей операции не заменяется вторым сотрудником. Вариант 1 выбран заказчиком в разборе эдж кейсов 8 октября; конкурентный прогон в двух сеансах ещё не выполнен.

### 3.2. Напоминание при «Провести и закрыть»

При каждом нажатии «Провести и закрыть», независимо от наличия связи, показать вопрос **«Вы создали задачу в Битрикс24?»** с ответами «Да» и «Нет».

Кнопка «Отмена» и Esc закрывают вопрос, оставляя заказ открытым без проведения этой командой. Отдельная кнопка отмены обеспечивает штатную обработку Esc в 1С; она не является ответом «Нет».

Оба ответа продолжают штатное проведение и закрытие, с обычными проверками и возможным отказом 1С. Они не вызывают API, не открывают Б24, не устанавливают признак создания и не привязывают задачу. Ответ «Нет» не препятствует работе: задачи нужны не для всех заказов. При следующем нажатии вопрос повторяется, включая заказ с существующей связью.

Обычные «Записать» и «Провести» без закрытия не показывают это напоминание и не создают задачу. Закрытие формы без нажатия кнопки создания также не создаёт задачу.

## 4. Форма заказа, список и связь

Прежний нижний блок прототипа убрать. Под верхними штатными командами формы («Провести и закрыть», «Провести» и др.) разместить кнопку **«Создать задачу в Битрикс24»**.

Рядом с верхними командами разместить компактные сведения о задаче, без восстановления прежнего нижнего диагностического блока:

- «Задача создана» — признак только для чтения, устанавливаемый по подтверждённой сохранённой связи, включая ручную привязку;
- «ID задачи Б24» — идентификатор связанной задачи;
- «Название задачи Б24» — название, полученное при создании или проверенной ручной привязке.

При отсутствии связи признак не установлен, ID и название пусты. Пока выполняется создание, показать «Создаём задачу»; при неизвестном результате — «Проверяем, создана ли задача». Отсутствие установленного признака в этих состояниях не означает отсутствия задачи. После повторного открытия формы состояние берётся из сохранённой операции. Ответы «Да»/«Нет» в напоминании эти сведения не изменяют. Если подтверждён ID созданной задачи, но связь ещё не записана, отдельно показать состояние «Задача №{ID} создана. Связь с заказом ещё не сохранена». Этот ID берётся из устойчивой операции; признак и поля сохранённой связи остаются незаполненными до её записи. Название хранится как снимок при создании или привязке; переименование задачи в Б24 не обновляет название в 1С и не нарушает связь по ID.

В списке «Заказы клиентов» сохранить видимую по умолчанию колонку «Задача Б24» сразу после «Клиент». Показывать обычный текст `Задача №{ID}` без гиперссылки и без запуска Б24. Без связи ячейка пуста. Форма и список используют одну сохранённую связь; после обновления показывают актуальные данные. Полный адрес хранится в связи, отдельное нижнее поле адреса не требуется.

Связь строго один к одному: один заказ связан с одной задачей, одна задача — с одним заказом. Проверка уникальности и запись атомарны для REST-результата, ручной привязки и изменения связи. Повтор одной операции безопасен; существующая связь не заменяется молча.

Ручную привязку существующей задачи, «Изменить связь» и «Удалить связь» сохранить в меню «Ещё». Проверять настроенный портал и корректный ID; отдельно учитывать доступность задачи. Недоступность Б24 и отсутствие прав не означают удаления задачи. Для привязки получить ID и название существующей задачи без изменения её данных; если получение невозможно, связь не подменять и показать причину.

Если задача уже создана вручную в Б24, сотрудник привязывает её через «Ещё → Привязать существующую задачу» до нажатия команды создания. Дополнительный вопрос «Создать новую или привязать существующую» перед первым созданием не показывается; подтверждение после явного удаления прежней связи описано в §3.1. Интеграция не распознаёт вручную созданную задачу без связи по совпадению названия: нажатие команды при отсутствии связи и незавершённой попытки создаёт новую задачу. Защита от повторов относится к операциям интеграции, а не к произвольным ручным задачам. Этот вариант подтверждён заказчиком при разборе эдж кейсов 8 октября.

Изменение и удаление требуют права изменения заказа и подтверждения. Фиксировать пользователя, время, прежнюю и новую связь; при удалении новая связь пуста. Сама задача Б24 при удалении связи не удаляется. Историю с ID последней удалённой связи сохранять для подтверждения следующего создания; наличие истории не заменяет проверку текущей связи и незавершённой попытки. Ручная привязка и исправление не запускают создание задачи или повторное проведение заказа.

Если во время ручного действия другой сотрудник изменил связь, остановить устаревшее действие и обновить только сведения интеграции, сохранив введённые изменения заказа. Сообщить об изменении связи и показать актуальный ID, если связь существует; при отсутствии связи явно сообщить об этом. Для дальнейшего изменения сотрудник заново запускает команду. Автоматического нового вопроса о замене связи и повторного применения прежнего выбора нет. Вариант 1 выбран заказчиком 10 октября при разборе этапа 4; конкурентный пользовательский прогон ещё не выполнен.

Задачу, созданную интеграцией для другого заказа, разрешено вручную привязать после завершения исходной операции и удаления прежней связи. В предпросмотре показать предупреждение «Эта задача создана для другого заказа. Данные задачи автоматически не изменятся» и получить явное подтверждение привязки. Происхождение определять по проверенному маркеру и сохранённой операции, а не по совпадению названия. Перед записью повторно проверить происхождение, завершённость операции и текущую занятость задачи; при незавершённой операции другого заказа или существующей связи с другим заказом привязка запрещена. Данные задачи сотрудник исправляет самостоятельно в Б24; автоматического изменения задачи нет. Вариант 1 выбран заказчиком 10 октября при разборе этапа 4; предупреждение и пользовательский сценарий ещё не реализованы/не проверены.

Если для заказа сохранена связь с задачей, после успешной штатной отмены заказа показать неблокирующее напоминание «Заказ отменён. Проверьте связанную задачу №{ID} в Битрикс24». После успешной установки пометки на удаление — «Заказ помечен на удаление. Проверьте связанную задачу №{ID} в Битрикс24». Действие с заказом продолжается штатно; задача и связь сохраняются, Б24 автоматически не открывается, фокус не переключается. Сотрудник сам решает, что делать с задачей. При отсутствии связи, отказе или отмене самого действия напоминания нет; простое снятие проведения и обычное перепроведение не считаются отменой заказа. Этот вариант подтверждён заказчиком при разборе эдж кейсов 8 октября; точки подключения к штатной отмене и пометке на удаление ещё требуется проверить в демобазе.

При закрытии частично выполненного заказа с отменённым остатком и существующей связью показать отдельное неблокирующее напоминание «Часть позиций отменена. Проверьте связанную задачу №{ID} в Битрикс24». Задача и связь сохраняются; данные задачи сотрудник корректирует самостоятельно. Такой заказ не считать полностью отменённым: при отсутствии связи и незавершённой попытки создание по кнопке разрешено с обычными проверками и проведением. Без связи или при отказе/отмене закрытия напоминания нет. Вариант 2 выбран заказчиком 10 октября при разборе этапа 4; текущая реализация требует уточнения и живой проверки.

### Уточнения интерфейса этапа 3 — 9 октября 2026 года

- При существующей связи команда создания не сохраняет и не проводит заказ. При несохранённых изменениях сообщить: «Заказ уже связан с задачей №{ID}. Изменения заказа этой командой не сохранены. Задача не обновлена».
- Крестик и Esc в напоминании отменяют «Провести и закрыть»: заказ открыт, запись и проведение не запускаются.
- Новое создание из полностью отменённого заказа или заказа с пометкой на удаление запрещено. Проверять до проведения и повторно при резервировании; связь и отображение ID сохранять. Частично выполненный заказ с отменённым остатком не подпадает под этот запрет; уточнение этапа 4 от 10 октября имеет приоритет над прежним критерием жизненного цикла этапа 2.
- При подтверждённом сбое до сохранения операции оставить заказ проведённым, сообщить о незапущенном создании; автоматически не повторять. Неопределённость сначала сверять с журналом.
- Название показывать одной строкой с многоточием и полной подсказкой; ID и состояние полностью. Сохранённое название не сокращать.
- Ручная привязка требует показа проверенных ID, полного названия и номера заказа, затем явной кнопки «Привязать». Завершённая задача допускается после предупреждения и подтверждения, без изменения статуса. Перед записью повторно проверить кандидата и конфликт связи.
- Для ещё не записанного заказа ручная привязка отклоняется: «Для привязки задачи сначала запишите заказ». Автоматической записи и проведения нет.
- Обновление сведений интеграции не перечитывает документ целиком и сохраняет введённые изменения.

## 5. Данные новой задачи

| Поле | Правило |
| --- | --- |
| Название | Новый формат: `{Контрагент}. Счета на Оплату №{НомерЗаказа} от {ДатаЗаказа} на {СуммаЗаказа} {ВалютаЗаказа}`. Номер, дата и сумма — из сохранённого заказа; номер с ведущими нулями, дата ДД.ММ.ГГГГ, сумма с двумя знаками после запятой, десятичной запятой и пробелами между разрядами; рядом код валюты заказа (например, KZT). Источник наименования — поле «Контрагент» заказа. Валюта и этот источник выбраны заказчиком 10 октября |
| Описание | Номер и дата заказа, клиент, сумма с валютой и ссылка на документ 1С; прежний состав данных сохраняется |
| Постановщик | Всегда Оксана при создании через интеграцию, независимо от сотрудника 1С и владельца вебхука |
| Исполнитель (ответственный) | Люда |
| Проект | Целевой — «ГЕМ Общие вопросы»; его точный ID и права ещё проверить. Проверенная тестовая среда — существующий «Гем платежи демо»; его прогоны не подтверждают применение целевого проекта |
| Наблюдатели | Инга |
| Соисполнители | Женя |
| Крайний срок | 19:00 по времени Казахстана (UTC+5): если новая попытка начинается до 19:00 — текущий день; с 19:00 — следующий календарный день, включая выходные и праздники |

Данные берутся из успешно проведённого и сохранённого заказа перед первой отправкой запроса. Номер, дата и сумма в новом названии относятся к этому заказу. Для начала названия использовать представление поля «Контрагент» заказа. Поле «Клиент» (реквизит «Партнер») по-прежнему используется отдельно в описании. Сумму брать после успешного проведения из сохранённого заказа, а не из несохранённой формы или отдельного счёта. Соответствие полей «Контрагент» и «Клиент» проверено в демобазе на этапе 0; для другой конфигурации его проверить повторно. Дата заказа в описании не заменяется текущей датой. Данные и срок операции сохраняются для восстановления; повтор после полуночи не меняет прежнюю попытку.

Согласованный формат названия сохранять с полным наименованием контрагента; автоматическое сокращение перед отправкой в Б24 не вводится. Это решение подтверждено заказчиком 10 октября после обсуждения длинного названия. Допустимую длину и сохранность всех частей нового названия проверить на целевой версии портала; численный предел пока не подтверждён. При достоверном выявлении превышения проверенного предела до отправки остановить создание с понятной причиной, сохранив успешное проведение заказа. Сокращение строки с многоточием в форме 1С относится только к отображению и не меняет сохранённое название.

Если во время фонового создания или восстановления связи заказ изменили и сохранили, задача остаётся с первоначальным снимком данных. При подтверждённом завершении и записи связи однократно сравнить актуальные сохранённые значения исходного заказа со снимком попытки только по данным, фактически передаваемым в актуальные название и описание задачи. Состав сравниваемых реквизитов должен соответствовать выбранному источнику наименования клиента и остальным передаваемым полям; изменения неиспользуемого реквизита не должны вызывать предупреждение. При расхождении дополнительно показать неблокирующее предупреждение «Данные заказа изменились после начала создания. Проверьте данные задачи №{ID}», без открытия окон и переключения фокуса. Изменение реквизитов, не передаваемых в задачу, предупреждение не вызывает. Задача и снимок автоматически не изменяются, новая задача не создаётся; постоянное наблюдение за дальнейшими изменениями заказа не вводится. Вариант с предупреждением подтверждён заказчиком при разборе эдж кейсов 8 октября; реализация и живой прогон ещё не выполнены.

Правило срока уточнено заказчиком при разборе эдж кейсов 8 октября: после 19:00 использовать завтра, 19:00, без переноса на рабочий день. Граница включена в перенос: новая попытка в 18:59:59 получает сегодня, 19:00; в 19:00:00 и позже — завтра, 19:00. При переходе месяца или года использовать следующий календарный день. Срок фиксируется при начале новой попытки после успешного проведения; время получения ответа и восстановление его не пересчитывают. Это согласованное требование, ещё не реализованное и не проверенное в приложениях.

Сотрудник может редактировать уже созданную задачу в Б24 в пределах штатных прав. Интеграция не возвращает исходные значения и не синхронизирует последующие изменения заказа с задачей. Отдельное окно ручной правки до REST-создания не входит в выбранный сценарий.

Уточнение 10 октября заменяет прежний состав участников: постановщик Оксана, исполнитель Люда, соисполнитель Женя, наблюдатель Инга. Кирилл в последнем уточнении не назначен участником задачи. Проверить и сохранить точные ID этих четырёх аккаунтов и проекта «ГЕМ Общие вопросы»; не выбирать только по именам или предположению о сокращённых именах. Не считать ID владельца вебхука или `user/30` ID постановщика. Прежние подтверждения ролей Евгения и Кирилла как наблюдателей относятся к предыдущему контракту.

Вебхук выполняет запрос с правами владельца. Новый состав — Оксана постановщиком, Люда исполнителем, Женя соисполнителем, Инга наблюдателем — проверить реальным запросом и перечитыванием результата на разрешённых тестовых объектах. Отдельно проверить доступ к целевому проекту, без автоматического добавления участников. Прежний успешный запрос с другими ролями и проектом не подтверждает новую схему. При нехватке прав не подменять Оксану владельцем вебхука или текущим сотрудником; зафиксировать препятствие. Возможность передать постановщика предусмотрена [документацией tasks.task.add](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-add.html), но доступ конкретного вебхука ещё не проверен.

При ручной привязке существующей задачи название, участники, проект и срок этой задачи не изменяются.

## 6. Обратное создание заказа — исключено

По решению пользователя от 1 октября 2026 года «Создать в КА» и создание нового заказа из задачи Б24 не входят в продукт. Раздел сохранён для стабильности нумерации. Возврат результата REST-создания и сохранение связи в существующем заказе обязательны.

## 7. Ошибки, повторы и совместная работа

- Ошибка проведения при создании кнопкой исключает отправку REST-запроса. Ошибка API, сохранения связи или открытия существующей задачи не отменяет уже успешное проведение.
- При достоверно подтверждённой неотправке запроса, например из-за отсутствия сети до отправки, показать «Задача не создана. Повторите позже» и завершить попытку как неотправленную. Не ставить её в очередь автоматической отправки после восстановления сети или следующего запуска клиента. Новая попытка запускается только повторным нажатием сотрудника, заново проводит заказ и использует актуальные сохранённые данные и новый срок по §5. Тайм-аут или потеря ответа после возможной отправки не доказывают неотправку и под это правило не попадают.
- Различать подтверждённую неотправку, подтверждённый отказ API до создания, неизвестный результат после отправки и созданную задачу с несохранённой связью. Не показывать успешное завершение до подтверждённой записи связи; при проблеме показать состояние и необходимое действие.
- Если задача создана, а связь ещё не записана, сразу показать «Задача №{ID} создана. Связь с заказом ещё не сохранена», сохранить подтверждённый ID в операции и автоматически восстановить связь с этой задачей. Полное уведомление об успехе показывается только после записи связи; создание заново запрещено. При неизвестном результате сначала проверять прежнюю операцию, показывать «Проверяем, создана ли задача» и временно блокировать повторное создание для данного заказа. Потеря ответа, повторное нажатие и повтор доставки результата не создают дубль. Другие заказы остаются доступны. При длительной недоступности Б24 или связи сохранять «Проверяем, создана ли задача» до подтверждения результата прежней попытки. При работающем клиенте автоматические проверки продолжаются в фоне; после закрытия клиента восстановление выполняется при следующем запуске. По фиксированному таймеру отдельное сообщение «Нужна проверка» и команда «Проверить результат» не вводятся. Прошедшее время не доказывает отсутствие задачи и не разрешает новое создание. Вариант 1 выбран заказчиком в разборе эдж кейсов 8 октября; прежние сроки восстановления при доступных системах сохраняются.
- До отправки сохранять устойчивые идентификаторы базы, заказа и операции, состояние и данные попытки. Подтверждённый ID задачи и факт записи связи также должны переживать закрытие клиента. Сопоставление по названию, сумме или порядку создания запрещено. Способ достоверного поиска задачи после потери ответа проверить прототипом; само наличие REST API не доказывает идемпотентность.
- Если проверка неизвестного результата долго не завершается, в форме оставить только текущее состояние «Проверяем, создана ли задача», без дополнительной подсказки об обращении к программисту. Порядок обращения и ручного разбора описать в инструкции для сотрудников и программиста. Само обращение, отсутствие задачи в результатах поиска и прошедшее время не разрешают повторную отправку. Вариант 1 выбран заказчиком 10 октября при разборе этапа 4.
- Атомарно проверять существующую связь и резервировать попытку для заказа; защитить проверку/запись уникальности от гонок. Конфликт результата не заменяет первую связь, не удаляет задачи и фиксируется в диагностике. Сложный интерфейс одновременного создания не разрабатывается; штатную блокировку формы не считать доказанной защитой.
- Запись связи не должна повторно проводить заказ, менять его данные, вызывать API создания или открывать Б24.
- Отдельный флажок отказа от задачи не вводится. Отказ состоит в ненажатии кнопки создания; «Нет» в напоминании не запрещает создать задачу позже. Признак «Задача создана» отражает связь, а не ответ сотрудника.
- При удалении задачи или отсутствии доступа связь сохраняется, новое создание автоматически не разрешается. Проверка доступности показывается отдельно; исправление — через команды связи с подтверждением. Отсутствие прав не считать удалением.
- При доступных системах и работающем клиенте сохранить связь не позднее 60 секунд после создания задачи. После закрытия клиента восстановить незавершённую связь не позднее 60 секунд после следующего запуска при доступных системах. Эти прежние сроки сохраняются; новый механизм ещё не проверен.
- Диагностика определяет заказ, операцию, этап и причину без секретного адреса вебхука, токенов и содержимого рабочей базы.

### Уточнения восстановления, согласованные при разборе этапа 2

- При незавершённой операции, неизвестном результате и известном ID без сохранённой связи ручная привязка, замена и удаление связи запрещены для исходного заказа. Обычная работа с заказом разрешена.
- При запуске клиента любым сотрудником восстанавливать незавершённые операции. Сообщение об успехе получает только инициатор первой попытки; при его отсутствии сохранить сообщение до следующего входа.
- Если инициатор потерял доступ к исходному заказу после отправки, результат и связь сохранить, но уведомление ему не показывать и не подтверждать доставку. При возвращении доступа доставить сохранённое уведомление с проверкой актуальной связи; общее сообщение без реквизитов не вводится. Сотрудникам с доступом сохранённый ID доступен в заказе и списке. Вариант 1 выбран заказчиком 10 октября при разборе этапа 4; живой сценарий отзыва и возвращения доступа ещё не проверен.
- Если заказ отменили или пометили на удаление во время попытки, при завершении предупредить; созданную задачу и связь сохранить. Снятие проведения не считать отменой заказа.
- При ручной привязке проверять точный маркер задачи: задачу незавершённой операции другого заказа привязывать запрещено.
- Отложенное сообщение должно сообщать, что связь впоследствии изменили или удалили. Доставка сообщения не восстанавливает прежнюю связь.
- При восстановлении предупредить об истёкшем фактическом сроке незавершённой задачи. Не предупреждать, если задачу завершили или срок перенесли в Б24.
- Показ подтверждать устойчиво после вызова уведомления. При аварии между показом и подтверждением допускается повтор сообщения при следующем входе; повтор создания запрещён.
- Задачи создают по одной; группировка накопленных уведомлений и работа одного сотрудника в двух одновременных сеансах не входят в приёмку.
- После восстановления старой резервной копии программист вручную отключает создание, сверяет потерянные связи и только затем включает создание. Автоматическое обнаружение отката базы не требуется.

## 8. Реализация и передача

Сторону 1С выполнить расширением без изменения основной конфигурации. Элементы формы и списка, напоминание, проведение перед созданием, настройки и хранение связи/операций реализовать в расширении. Сохранить штатные проверки, запись, проведение и закрытие. Для хранения использовать собственные регистры расширения с атомарной защитой; пригодность имеющегося прототипа подтвердить для нового контракта.

Создание выполняется через предоставленный входящий вебхук. Прямой HTTPS-обмен из расширения — первый кандидат для проверки; место исполнения, безопасное хранение секрета и восстановление после потери ответа ещё не выбраны технически. Python-служба исключена решением 7 октября и не возвращается новым планом. Приложение, `entity`, OAuth и worker прежнего прототипа не являются обязательными компонентами REST-сценария. Если понадобятся дополнительные компоненты или иной способ доработки 1С, согласовать состав, размещение, стоимость и доступы до их включения и внедрения.

Разработка и текущие проверки — в существующей «КА Демо». Совместимость с рабочей базой проверить перед внедрением. Открытие задач из 1С исключено. Если возможностей расширения недостаточно, отдельно согласовать иной способ; основную конфигурацию без такого согласования не менять.

Передать программисту:

1. Проверенный `.cfe` с версиями платформы/конфигурации и режимами совместимости.
2. Исходники, перечень собственных и заимствованных объектов, реквизитов, процедур и точек подключения.
3. Инструкции установки, настройки вебхука, проверенных ID, хранения секрета и рабочих мест.
4. Сценарии и фактические результаты проверки, включая восстановление, права и ограничения.
5. Документацию дополнительных компонентов, только если их использование отдельно согласовано.

Портал, адрес базы и доступы задавать настройками. Секрет не включать в исходники, `.cfe`, логи и публикуемые инструкции. Штатные права 1С определяют возможность изменения/проведения заказа и использования интеграции; REST действует в пределах прав владельца вебхука. Требуется проверка, что обычный сотрудник не получает возможности читать секрет или создавать задачи по недоступным ему заказам.

После успешной проверки программист устанавливает расширение в рабочую базу с учётом существующих доработок и расширений. Поставка `.cf`, замена основной конфигурации и перенос через сравнение/объединение не входят в выбранный способ внедрения. Наличие старого `.cfe` не подтверждает новую поставку.

## 9. Приёмочные сценарии

| Проверка | Ожидаемый результат |
| --- | --- |
| Кнопка и сведения в форме | Кнопка под верхними командами; рядом признак создания, ID и название; команды открытия нет; прежнего нижнего блока нет |
| Создание кнопкой из нового или изменённого заказа | Сначала штатные проверки и успешное проведение, затем REST по сохранённым данным; предварительная форма задачи не открывается |
| Ошибка или отмена проведения при создании | REST не вызывается, задача не создаётся |
| Создание из проведённого заказа | Задача создаётся только по кнопке; одна сохранённая связь с исходным заказом |
| Фоновое создание и закрытие формы | После успешного проведения и сохранения операции REST-ожидание не блокирует интерфейс; доступны другой заказ и закрытие исходной формы; попытка сохраняется, повторное создание для неё блокируется |
| Повторное открытие формы до результата | Показано сохранённое состояние «Создаём задачу» или «Проверяем, создана ли задача»; новая попытка не отправляется |
| «Провести и закрыть», ответ «Да» | Показан вопрос; штатные проведение и закрытие продолжаются; API и Б24 не запускаются, сведения связи не меняются |
| «Провести и закрыть», ответ «Нет» | Тот же результат; отсутствие задачи не препятствует проведению и закрытию |
| «Провести и закрыть» при существующей связи | Вопрос также показан; оба ответа не создают новую задачу |
| Повторное «Провести и закрыть» | Вопрос повторяется независимо от прежнего ответа |
| Штатный отказ после ответа на напоминание | Ответ не обходит проверки и не отменяет штатный отказ; REST не вызывается |
| Крестик или Esc напоминания | Команда отменена; заказ не проводится и не закрывается этой командой, REST не вызывается |
| Только «Записать», «Провести» или закрытие формы | Напоминание и создание задачи не запускаются |
| Подтверждённое создание | ID, ссылка и название сохранены; признак установлен; неблокирующее уведомление «По заказу №{НомерЗаказа} от {ДатаЗаказа} создана задача №{ID}» только после записи связи; окна не открываются, фокус не переключается |
| Уведомление при закрытой форме или другом активном заказе | Сообщение содержит номер/дату исходного заказа и его ID задачи, не требует «ОК», не переключает окна; связь и сведения относятся только к исходному заказу, текущая работа продолжается |
| Заполнение новой задачи | Новый формат названия по §5 с наименованием клиента, номером, датой и суммой сохранённого заказа; описание по §5; Оксана постановщик, Люда исполнитель, Женя соисполнитель, Инга наблюдатель; целевой проект «ГЕМ Общие вопросы». Фактическую среду и проект прогона указать; демопроект не считать доказательством применения целевого проекта |
| Несколько заказов одного клиента | В названии каждой задачи указаны номер, дата и сумма её исходного заказа; связь сохраняется по ID задачи, совпадение названий не используется для поиска/привязки |
| Крайний срок | По времени начала новой попытки в UTC+5: до 19:00 — сегодня, 19:00; с 19:00 — следующий календарный день, 19:00, включая выходные и праздники; восстановление после полуночи не меняет срок прежней операции |
| Граница срока и календарные переходы | Новые попытки в 18:59:59, 19:00:00 и 19:00:01 получают срок по §5; проверены переход на выходной, новый месяц и год; время ответа не сдвигает срок |
| Создание разными сотрудниками | Оксана остаётся постановщиком, остальные роли и проект также соблюдены; действуют права 1С и владельца вебхука |
| Недостаточные права или неверные настройки | Понятная ошибка без секрета; участников не подменяют; успешное проведение не отменяется |
| Десктопный Б24 закрыт или отсутствует при создании | REST-создание работает при доступном API; приложение и браузер не запускаются |
| Повторная кнопка при существующей связи | Новая задача не создаётся, имеющаяся связь сохраняется; показана существующая задача |
| Повторная кнопка при существующей связи и изменённой форме | Заказ не записывается и не проводится; сообщается ID, несохранённые изменения и отсутствие обновления задачи |
| Новое создание для отменённого или помеченного заказа | Отказ до проведения и повторная проверка при резервировании; существующая связь и отображение ID сохраняются |
| Сбой запуска до устойчивой операции после проведения | Проведение сохраняется; после чтения журнала подтверждённая неотправка допускает только ручной повтор, неопределённое состояние запрещает новую отправку |
| Длинное название задачи | В форме 1С одна строка с сокращением и многоточием, полное название в подсказке; ID и состояние читаются полностью. В Б24 передаётся согласованный формат с полным наименованием контрагента; допустимая длина и сохранность всех частей проверены отдельно; достоверное превышение проверенного предела до отправки прекращает создание с понятной причиной и сохраняет проведение |
| Предпросмотр ручной привязки | Показаны ID, полное название и номер исходного заказа; явное «Привязать»; при сохранении повторная проверка кандидата, прав и версии |
| Ручная привязка завершённой задачи | Предупреждение и подтверждение; статус задачи не меняется |
| Привязка к новому незаписанному заказу | Отказ с указанием сначала записать заказ; нет автоматической записи или проведения |
| Обновление сведений при изменённом заказе | Введённые данные и признак модификации сохранены; обновляются только сведения интеграции |
| Потеря ответа после отправки | Результат неизвестен; прежняя операция проверяется, повторное создание заблокировано; дубль не создаётся; при длительной недоступности остаётся «Проверяем, создана ли задача», проверки продолжаются при работающем клиенте, таймер не разрешает повтор и не вводит отдельного сообщения/команды |
| Созданная задача при ошибке записи связи | Сразу показано «Задача №{ID} создана. Связь с заказом ещё не сохранена»; ID сохранён в операции, признак сохранённой связи не установлен; связь автоматически восстанавливается с тем же ID без повторного проведения и создания; полное уведомление только после записи связи |
| Подтверждённая неотправка запроса | «Задача не создана. Повторите позже»; автоматической отправки после восстановления сети или нового запуска нет; повторный клик запускает новую попытку с актуальными проведёнными данными и сроком; возможная отправка/тайм-аут остаются неизвестным результатом |
| Повтор результата или восстановления | Та же операция и связь, без дубля и молчаливой замены |
| Одновременные попытки и конфликт связи | Атомарная защита попытки/связи; первая связь сохранена, конфликт диагностирован, задачи не удаляются; второму сотруднику показано «Задача уже создаётся», нового запроса создания нет; уведомление успеха только инициатору первой попытки, второму та же связь доступна после обновления; инициатор операции не заменяется |
| Признак создания и обновление формы | Признак/ID/название берутся из сохранённой связи; «Да» не устанавливает признак; неизвестный результат показан отдельно |
| Колонка списка | После «Клиент» видна `Задача №{ID}`, без связи пуста; форма и список читают одну связь |
| ID в форме и списке | Показан ID сохранённой связи; кнопки открытия и гиперссылки нет; Б24 и браузер из 1С не запускаются |
| Ручная привязка через «Ещё» | Проверены портал, ID, название и уникальность; данные существующей задачи не меняются |
| Перенос задачи интеграции к другому заказу | После завершения исходной операции и удаления прежней связи перенос разрешён с предупреждением о происхождении и неизменности данных задачи, затем явным подтверждением; проверки повторены перед записью; незавершённая операция или текущая связь другого заказа исключают перенос |
| Задача ранее создана вручную | После явной привязки новая задача не создаётся; без привязки совпадение названия не заменяет связь; перед первым созданием дополнительного вопроса нет |
| Неверная или занятая ссылка | Привязка отклонена, прежняя связь сохранена |
| Изменение/удаление связи и отмена | Право изменения, подтверждение и аудит; отмена сохраняет связь; задача Б24 не удаляется |
| Конкурентное ручное изменение связи | Устаревшее действие остановлено, результат первого действия сохранён; обновлены только сведения интеграции с актуальным ID или отсутствием связи, введённые данные заказа сохранены; для нового изменения сотрудник заново запускает команду, автоматического повторного подтверждения нет |
| Новое создание после явного удаления связи | До проведения показано подтверждение с ID последней удалённой связи; отмена не проводит заказ этой командой и не создаёт задачу; после подтверждения текущая связь и попытка повторно проверены атомарно; прежняя задача Б24 сохраняется |
| Переименование связанной задачи в Б24 | В 1С остаётся название, сохранённое при создании или привязке; ID связи сохранён; синхронизации названия нет |
| Удалённая или недоступная задача | Связь сохраняется; отсутствие прав не считается удалением и не разрешает новое создание |
| Длительная проверка неизвестного результата | В форме только «Проверяем, создана ли задача», без дополнительной подсказки об обращении к программисту; прошедшее время и нулевой результат поиска не разрешают повторную отправку |
| Отмена заказа или пометка на удаление при существующей связи | После успешного штатного действия показано неблокирующее напоминание с ID связанной задачи и текстом соответствующего действия; задача и связь сохраняются; окна не открываются, фокус не переключается |
| Закрытие частично выполненного заказа с отменённым остатком | При связи отдельное неблокирующее напоминание «Часть позиций отменена. Проверьте связанную задачу №{ID} в Битрикс24»; задача и связь сохраняются; без связи создание разрешено с обычными проверками, напоминания нет; отказ/отмена закрытия не вызывают напоминание |
| Исключения для напоминания об отмене | Без связи, при отказе/отмене самого действия, простом снятии проведения и обычном перепроведении напоминания нет |
| Изменения заказа или задачи после создания | Интеграция не синхронизирует данные и не возвращает прежние значения |
| Изменение заказа во время создания/восстановления | В задаче сохранён первоначальный снимок; после записи связи при расхождении передаваемых данных показано неблокирующее предупреждение с ID задачи; без изменения данных или при изменении только непередаваемых реквизитов предупреждения нет; задача не изменяется и не создаётся повторно |
| Срок возврата при работающем клиенте | При доступных системах связь сохранена ≤60 секунд после создания |
| Клиент закрыт до записи связи | Устойчивая попытка восстановлена и связь сохранена ≤60 секунд после следующего запуска при доступных системах |
| Права обычного сотрудника | Штатные права заказа соблюдены, секрет недоступен для чтения; новые роли и создание проверены фактически |
| Отзыв доступа инициатора после отправки и возвращение доступа | Результат и связь сохранены; до возвращения доступа уведомления нет и доставка не подтверждена; после возвращения доступа инициатор получает сохранённое уведомление с учётом актуальной связи |
| Установка и новый сеанс | Проверенный `.cfe` применён без изменения основной конфигурации; функции работают без EPF, MCP и Python-службы |

Проверки выполнять в «КА Демо» и существующем демопроекте на тестовых объектах. Для REST проверять реальную сохранённую задачу; в 1С проверять отображение её ID и отсутствие команд перехода. Зафиксировать версии платформы, конфигурации, режимов совместимости, клиента 1С и ОС. Статические проверки, моки и прежние прогоны не заменяют приёмку нового сценария. Непроверенные строки остаются открытыми.

## 10. Технические вопросы и условия приёмки

Новый пользовательский сценарий согласован, техническая реализация ещё не подтверждена. Требуется:

- Проверить текущий вебхук, фактические scopes и права владельца; подтвердить ID четырёх участников по актуальному §5 и целевого проекта «ГЕМ Общие вопросы», сохранив отдельную демосреду для живых тестов. Создать и перечитать тестовую задачу с точными ролями, без добавления участников в проект и изменения рабочих объектов.
- Проверить безопасный HTTPS-обмен из расширения на платформе демобазы: место исполнения, хранение настроек и секрета, штатные права. Новая архитектура не должна зависеть от удалённой Python-службы.
- Подтвердить фоновое создание на файловой демобазе: REST-ожидание не блокирует интерфейс, закрытие формы не теряет операцию, следующий запуск клиента восстанавливает незавершённую попытку. Дополнительные компоненты без отдельного согласования не подключать.
- Подтвердить точку выполнения штатного проведения из команды создания и порядок «успешное проведение → REST», включая новые документы, несохранённые изменения, отказ и отмену. Напоминание при «Провести и закрыть» проверить отдельно для обоих ответов, существующей связи и закрытия самого диалога.
- Установить и проверить точки штатной отмены заказа и установки пометки на удаление: напоминание только после успешного действия при существующей связи; отличать отмену заказа от простого снятия проведения и перепроведения.
- Подтвердить верхнее размещение кнопки/сведений, удаление нижнего блока и отключение прежнего автоматического открытия/очереди. Незавершённые старые операции не переносить в новый поток автоматически.
- Выбрать и проверить устойчивое хранение новой попытки до отправки, атомарное резервирование, сопоставление после потери ответа и запись ID/ссылки/названия без повторного проведения. Нельзя считать REST-метод гарантией отсутствия дублей; при неизвестном результате создавать повторно запрещено.
- Проверить возврат и восстановление при закрытой форме и клиенте 1С, оба срока 60 секунд и конкурирующие сеансы.
- Перед внедрением проверить версии рабочей базы, доработки, расширения, режимы совместимости, права и ОС сотрудников.

Прототипы и независимую разработку продолжать; неподтверждённые механизмы фиксировать как открытые приёмочные пункты, не выдавать за готовую интеграцию. Дополнительные компоненты согласовать до включения в пользовательский поток. Фактические результаты вести в `docs/stage-1-prototypes.md` с датой, средой, исходным сбоем и успешной повторной проверкой.

## 11. За пределами первой версии

- Автоматическое создание или открытие формы новой задачи при «Провести и закрыть», записи, проведении или ответах на напоминание.
- Предварительная форма редактирования новой задачи в 1С или Б24; создание по шаблонам задач.
- Любое открытие задач из 1С, включая десктопное приложение и браузер.
- Формирование Word-документов и автоматическая передача файлов из 1С в Б24.
- Счета на оплату внутри Б24; выставление счетов остаётся в КА.
- Несколько связанных задач у одного заказа.
- Создание заказов из Б24, включая «Создать в КА», автоматический подбор клиента и заполнение строк заказа из Б24.
- Синхронизация статусов, сроков, платежей, названия и содержимого заказа/задачи после создания.
- Возврат удалённой Python-службы и прежней схемы worker/entity как обязательной архитектуры.

## 12. Основания и приоритет требований

Основания: исходная задача Б24 №9866, предоставленная переписка, исторические прототипы и ответы заказчика. Последние согласованные решения имеют приоритет: уточнения этапа 4 от 10 октября заменяют прежние название, целевой проект, участников и критерий полной отмены; решения 8–9 октября об отдельной кнопке, напоминании и отсутствии переходов сохраняются. Историю фактических проверок сохранять, не засчитывать её как приёмку нового REST-сценария.

Актуальные решения: документ «Заказ клиента»; расширение без изменения основной конфигурации, поставка `.cfe`; кнопка под верхними командами сначала проводит заказ, затем создаёт задачу через вебхук; при «Провести и закрыть» всегда вопрос, оба ответа продолжают штатное действие без создания; задачи необязательны; после создания сообщение в 1С, без автоматического открытия Б24; признак создания, ID и название в верхней части формы, колонка после «Клиент»; связь один к одному с ручным исправлением через «Ещё» и восстановлением без дубля.

В разборе эдж кейсов подтверждены создание в фоне после успешного проведения с возможностью продолжить работу или закрыть форму и блокировкой повторного создания только для того же заказа, а также ручная привязка ранее созданной задачи через «Ещё» без дополнительного вопроса перед созданием. Успех сообщается неблокирующим уведомлением с номером/датой исходного заказа и ID задачи после записи связи, без открытия окон и переключения фокуса, в том числе при закрытой форме или работе с другим заказом. При изменении и сохранении передаваемых данных заказа во время попытки дополнительно предупреждать о расхождении с первоначальным снимком; данные задачи автоматически не изменять. После успешной отмены заказа или установки пометки на удаление при существующей связи показывать неблокирующее напоминание о задаче, сохраняя задачу и связь. При конкурентном нажатии второй сотрудник получает «Задача уже создаётся» без нового запроса; уведомление успеха только инициатору первой попытки, второму результат доступен после обновления. При известном ID и ошибке записи связи сразу показывать ID с сообщением о несохранённой связи и автоматически восстанавливать её; полное уведомление только после записи. Новое создание после явного удаления связи требует подтверждения с прежним ID. При подтверждённой неотправке автоматическая очередь исключена: сотрудник повторяет нажатием, с актуальными данными и сроком. Название в 1С остаётся снимком, переименование в Б24 связь по ID не меняет. Эти решения описывают требуемое поведение, а не результат проверки реализации.
